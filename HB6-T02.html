SPI — Modes, Multi-Slave, QSPI / OSPI

CPOL and CPHA decoded once and for all, chip-select strategies for single and multi-device buses, daisy-chain wiring, DMA-driven transfers, and the leap to quad and octal SPI for external flash.

The Serial Peripheral Interface is the oldest trick in the embedded playbook — four wires, full duplex, no addressing overhead — and it remains the fastest synchronous bus you can hang off a microcontroller without going to a dedicated high-speed interface. Flash memories, ADCs, DACs, displays, IMUs, and RF transceivers all speak SPI. Yet SPI has exactly one standard: Motorola's 1979 spec, which left the clock polarity and phase entirely to the implementer. The result is four incompatible clock modes and a 40-year tradition of engineers spending an afternoon staring at a logic analyser trying to figure out why the sensor is not responding.

This topic clears that up permanently, then covers everything that follows: how to manage multiple slaves on one bus, how to pipeline transfers with DMA, and how the SPI lineage evolved into Quad-SPI and Octal-SPI for feeding high-speed NOR flash to cache-hungry MCUs.

The four wires and what they do

A standard SPI bus has four signals. The naming varies by vendor — Motorola, Intel, and ARM all use slightly different mnemonics — but the function is always the same.

SPI is full duplex: every clock edge simultaneously shifts one bit out of the master and one bit into the master. Both sides maintain a shift register; at the end of N clock cycles both have exchanged N bits. If you only want to write to a slave, you ignore MISO. If you only want to read, you clock out dummy bytes (typically 0x00 or 0xFF) to generate the clocks the slave needs to push data back.

CPOL and CPHA — the four modes

Two bits control the clock relationship: CPOL (Clock Polarity) sets the idle state of SCLK, and CPHA (Clock Phase) decides which edge — leading or trailing — is used to sample data. The combination produces four modes, conventionally numbered 0 to 3.

The vast majority of sensors and memory devices use Mode 0 (CPOL=0, CPHA=0): clock idles low, data is driven by the master on the falling edge of CS̄ and on each falling edge of SCLK, and sampled by the slave on the rising edge. Mode 3 (CPOL=1, CPHA=1) is the other common choice — clock idles high, data is shifted on rising edges and sampled on falling — and it produces the same capture/shift relationship from the slave's perspective, just with the polarity inverted.

Key Idea

Mode 0 and Mode 3 are functionally equivalent from the slave's view of setup and hold timing — data is stable for the same fraction of the clock period in both. The only difference is whether idle SCLK is low or high. If a device says "SPI Mode 0 or Mode 3", it means it can tolerate either idle polarity and will still sample correctly. Always confirm with the datasheet's timing diagram — the tSU (setup) and tH (hold) numbers are what matter for reliability, not the mode number.

How to read the datasheet timing diagram

Every SPI peripheral datasheet contains a timing diagram. Reading it correctly prevents most mode-selection mistakes. Look for three things: the level of SCLK before CS̄ asserts (CPOL), whether the first data bit appears before the first clock edge or after it (CPHA=0 vs CPHA=1), and which edge has the arrow labelled "data valid" or "sample point".

Common Mistake

Some datasheets describe their SPI interface as "SPI-compatible" without naming the mode. They instead say something like "data is clocked in on the rising edge of SCK, with SCK idle low." That is Mode 0. When you see "clocked in on falling edge, SCK idle low" that is Mode 1. Translate prose to CPOL/CPHA yourself rather than guessing a mode number.

Chip-select strategies

CS̄ is the SPI bus's substitute for I2C addressing. Each slave gets its own dedicated CS̄ line from the master. The master selects a device by asserting (pulling low) its CS̄ line. All un-selected slaves hold their MISO lines in a high-impedance state, letting the selected device drive the shared bus without contention.

Single slave — the simple case

One master, one slave: one GPIO drives CS̄. The only subtlety is timing. The setup time between CS̄ assertion and the first SCLK edge (called tCSS or tCS-to-SCK) must satisfy the slave's minimum requirement, typically 20–100 ns. The hold time after the last clock edge before de-assertion (tCSH) must also be respected. When using a hardware SPI peripheral, the peripheral's NSS (or SS) output manages this automatically. When bit-banging, add a __NOP() or a short delay between GPIO writes.

Cspi_transfer.c — software CS with timing margin
#include "stm32f4xx_hal.h"

static inline void cs_assert(void)
{
    HAL_GPIO_WritePin(SPI_CS_GPIO_Port, SPI_CS_Pin, GPIO_PIN_RESET);
    /* tCSS: ≥ 20 ns for most sensors — 1 NOP @ 168 MHz ≈ 6 ns,
     * so 4 NOPs give comfortable margin */
    __NOP(); __NOP(); __NOP(); __NOP();
}

static inline void cs_deassert(void)
{
    /* tCSH: ≥ 50 ns before next transfer on many devices */
    __NOP(); __NOP(); __NOP(); __NOP(); __NOP(); __NOP(); __NOP(); __NOP();
    HAL_GPIO_WritePin(SPI_CS_GPIO_Port, SPI_CS_Pin, GPIO_PIN_SET);
}

HAL_StatusTypeDef spi_write_reg(uint8_t reg, uint8_t val)
{
    uint8_t buf[2] = { reg & 0x7F, val }; /* clear MSB = write command */
    cs_assert();
    HAL_StatusTypeDef st = HAL_SPI_Transmit(&hspi1, buf, sizeof(buf), 10);
    cs_deassert();
    return st;
}

HAL_StatusTypeDef spi_read_reg(uint8_t reg, uint8_t *val)
{
    uint8_t tx = reg | 0x80; /* set MSB = read command */
    uint8_t rx = 0;
    cs_assert();
    HAL_StatusTypeDef st = HAL_SPI_TransmitReceive(&hspi1, &tx, &rx, 1, 10);
    cs_deassert();
    *val = rx;
    return st;
}

Multi-slave — independent chip selects

The standard multi-device topology gives each slave its own dedicated CS̄ GPIO. SCLK, MOSI, and MISO are shared. Only one CS̄ is asserted at any time — driving two low simultaneously would put two slaves' MISO drivers in conflict.

The limitation is GPIO count. A microcontroller with one SPI peripheral can theoretically drive as many slaves as it has spare GPIO pins. In practice, three to six slaves on a single bus is comfortable; beyond that, bus capacitance degrades the signal quality at high speed and you should consider a second SPI peripheral or a dedicated demultiplexer IC.

Daisy-chain topology

Daisy chaining is the alternative when GPIO pins are scarce and you need to address several identical devices — shift registers (74HC595), LED drivers (TLC5940), or programmable logic devices are classic examples. All devices share a single CS̄ line. MOSI connects to the first device's data input; that device's serial output connects to the second device's input, and so on. MISO returns from the last device in the chain.

Daisy-chain topology — single CS, N devices Master ┌────────────┐ │ SCLK ──────┼───────────────────────────────────────────► │ CS̄ ──────┼───────────────────────────────────────────► (all slaves) │ │ ┌────────┐ ┌────────┐ ┌────────┐ │ MOSI ──────┼────►│ DIN │ │ DIN │ │ DIN │ │ │ │ Slave0 │ │ Slave1 │ │ Slave2 │ │ MISO ◄─────┼─────│ DOUT ─┼────►│ DOUT ─┼────►│ DOUT │ └────────────┘ └────────┘ └────────┘ └────────┘ ▲ ▲ ▲ SCLK & CS̄ connected in parallel

To program N daisy-chained devices, the master transmits N × word_size bits with CS̄ held low the entire time. Each clock shifts data one step further down the chain. When CS̄ rises, all devices latch the word that reached their input register. The first device in the chain receives the last byte transmitted; the last device receives the first byte. This reversal must be accounted for when assembling the transmit buffer.

Cdaisy_chain.c — write N 74HC595 shift registers
#define NUM_DEVICES  3

/* values[0] goes to the LAST device (first to latch when CS rises),
 * values[N-1] goes to the FIRST device in the chain.            */
void daisy_write(const uint8_t values[NUM_DEVICES])
{
    uint8_t buf[NUM_DEVICES];
    /* Reverse: last element of values → first byte on MOSI */
    for (int i = 0; i < NUM_DEVICES; i++)
        buf[i] = values[NUM_DEVICES - 1 - i];

    cs_assert();
    HAL_SPI_Transmit(&hspi1, buf, NUM_DEVICES, 10);
    cs_deassert();   /* rising edge latches data into all output registers */
}
Daisy-Chain Gotcha

Daisy chaining does not work if devices need to simultaneously output different data — the chain only works for devices where DOUT is a pure pass-through of previously received data, not a status response. ADCs and sensors with bidirectional SPI cannot be daisy-chained; use independent CS lines for those.

DMA-driven SPI transfers

Blocking SPI transfers (HAL_SPI_Transmit with a timeout) burn CPU cycles waiting for each byte to shift out. At 10 MHz and 8-bit frames, one byte takes 800 ns — time the CPU could be doing something else. DMA fixes this: configure the DMA controller to feed bytes to the SPI shift register autonomously, fire the transfer, and let the CPU continue until a DMA-complete interrupt signals that the buffer is done.

Cspi_dma.c — non-blocking DMA transmit (STM32 HAL)
volatile uint8_t spi_busy = 0;

/* Called from HAL_SPI_TxCpltCallback */
void HAL_SPI_TxCpltCallback(SPI_HandleTypeDef *hspi)
{
    if (hspi->Instance == SPI1) {
        cs_deassert();
        spi_busy = 0;
    }
}

/* Non-blocking transmit — caller must wait for spi_busy == 0 */
HAL_StatusTypeDef spi_transmit_dma(uint8_t *buf, uint16_t len)
{
    if (spi_busy) return HAL_BUSY;
    spi_busy = 1;
    cs_assert();
    /* DMA feeds bytes into SPI->DR autonomously */
    return HAL_SPI_Transmit_DMA(&hspi1, buf, len);
}

/* Usage */
void display_refresh(void)
{
    /* frame_buf is SRAM — must remain valid until spi_busy == 0 */
    while (spi_busy) {}          /* wait for prior frame */
    spi_transmit_dma(frame_buf, sizeof(frame_buf));
    /* CPU is free to do other work now */
}
DMA Buffer Rules — Critical

On Cortex-M7 (STM32H7, i.MX RT) the D-cache and DMA controller operate independently. If frame_buf is in a cached region, the CPU's writes may sit in cache and never reach SRAM before DMA reads it — producing corrupted output. The fix is to either place DMA buffers in a non-cacheable memory region (configured via MPU), or manually call SCB_CleanDCache_by_Addr() before starting the transfer. This is one of the most common sources of hard-to-reproduce SPI bugs on M7-class devices.

Timing, speed, and signal integrity

SPI has no formal maximum speed in its original spec — it is limited by the weakest link on the bus. In practice, four factors determine how fast you can reliably run.

PCB trace capacitance

Each millimetre of FR4 trace adds roughly 0.5–1 pF. At 50 MHz and a typical 10 Ω drive impedance, the RC time constant from 10 Ω × 20 pF = 0.2 ns — well within budget. At 100 MHz over 100 mm of trace, you start to need controlled impedance and termination. For most embedded SPI at under 20 MHz over under 50 mm, this is not a concern.

Slave input clock frequency limit

Every SPI slave datasheet specifies a maximum fSCLK. Flash memories might tolerate 133 MHz in fast-read mode. A low-cost ADC might cap at 20 MHz. The master must not exceed the slowest device on the shared bus.

GPIO toggle rate (bit-banged SPI)

On an STM32F4 running at 168 MHz, a tight GPIO toggle loop achieves roughly 21 MHz per bit — around 2.6 Mbit/s for 8-bit frames with the loop overhead. Hardware SPI peripheral at the same clock can reach 42 MHz (APB2/2). If you need speed, always use the hardware peripheral.

The NSS (Slave Select) hardware pin gotcha

STM32 SPI peripherals have a hardware NSS pin. In NSS hardware mode, the peripheral drives NSS automatically — but it de-asserts between every byte if the data size is 8 bits, which is almost never what you want for multi-byte transfers. The standard approach is to configure NSS as software-controlled (SPI_NSS_SOFT) and drive a regular GPIO manually, giving full control over when CS̄ asserts and de-asserts.

Quad-SPI and Octal-SPI — feeding the flash cache

Standard SPI sends one bit per clock cycle on MOSI. When an MCU executes code from external NOR flash — a common architecture on resource-constrained parts where internal flash is too small — a 133 MHz SPI gives at most 133 Mbit/s = 16 MB/s of read bandwidth. That sounds fast, but a Cortex-M7 at 480 MHz can fetch instructions much faster than a serial flash can supply them. The answer is to widen the data bus.

Dual SPI — 2 data lines

Dual SPI adds a second data line, so two bits transfer per clock. MOSI and MISO both become bidirectional data lines (IO0 and IO1) during the data phase, doubling throughput to 266 Mbit/s at 133 MHz. The command and address phases are still single-line.

Quad SPI (QSPI) — 4 data lines

QSPI uses four IO lines (IO0–IO3) simultaneously during the data phase — four bits per clock, quadrupling standard SPI throughput. At 133 MHz that is 532 Mbit/s ≈ 66 MB/s, which is enough to comfortably supply a 480 MHz Cortex-M7 instruction fetch. The STM32H7's QUADSPI peripheral supports this natively. The flash must support quad mode and be explicitly put into it with a Write Enable → Write Status Register sequence before quad reads work.

OSPI extends the concept to eight simultaneous data lines (IO0–IO7). One clock cycle transfers one full byte. At 200 MHz DDR (both clock edges used), OSPI delivers 400 MT/s = 400 MB/s — enough to sustain even Cortex-A-class instruction fetch from external flash. The STM32U5 and some NXP i.MX RT parts include OSPI peripherals. The PCB layout demands careful attention to trace length matching and controlled impedance at these speeds.

Memory-mapped (XIP) mode

QSPI and OSPI peripherals on modern MCUs support a memory-mapped mode, also called Execute-in-Place (XIP). The peripheral sits at a fixed address range in the CPU's memory map (e.g., 0x90000000 on STM32H7). When the CPU fetches an instruction or reads data from that range, the QSPI peripheral automatically translates the access into a fast-read SPI transaction, caches the result in a small internal FIFO, and returns the data with minimal latency. From the CPU's perspective, external flash looks like ordinary SRAM. The penalty is one burst miss latency; subsequent accesses into the same cache line are served at full bus speed.

Cqspi_init.c — STM32H7 QUADSPI in memory-mapped mode
#include "stm32h7xx_hal.h"

static QSPI_HandleTypeDef hqspi;

HAL_StatusTypeDef qspi_memory_map(void)
{
    QSPI_CommandTypeDef      cmd  = {0};
    QSPI_MemoryMappedTypeDef mmap = {0};

    /* W25Q128 quad fast-read: opcode 0xEB, 4-byte address,
     * 4-line address + data, 6 dummy cycles                */
    cmd.InstructionMode   = QSPI_INSTRUCTION_1_LINE;
    cmd.Instruction       = 0xEB;          /* QPI fast read */
    cmd.AddressMode       = QSPI_ADDRESS_4_LINES;
    cmd.AddressSize       = QSPI_ADDRESS_24_BITS;
    cmd.AlternateByteMode = QSPI_ALTERNATE_BYTES_NONE;
    cmd.DataMode          = QSPI_DATA_4_LINES;
    cmd.DummyCycles       = 6;
    cmd.DdrMode           = QSPI_DDR_MODE_DISABLE;
    cmd.SIOOMode          = QSPI_SIOO_INST_EVERY_CMD;

    mmap.TimeOutActivation = QSPI_TIMEOUT_COUNTER_DISABLE;

    return HAL_QSPI_MemoryMapped(&hqspi, &cmd, &mmap);
    /* After this call, 0x90000000 aliases the flash array.
     * Linker can place code or read-only data at 0x90xxxxxx. */
}
Key Idea

Once QSPI memory-mapped mode is active, the MCU's ART accelerator (on STM32 parts) or I-cache (on Cortex-M7) works on the XIP region just as it does on internal flash. The typical measured throughput for sequential instruction fetch from a W25Q128 at 133 MHz QSPI on an STM32H743 is around 50–55 MB/s — more than adequate for most application code. Only the most compute-intensive inner loops benefit from being placed in SRAM or ITCM.

Selecting the right SPI topology

Before writing a single line of driver code, answer four questions: how many slaves, do they all use the same mode, how fast do you need the bus, and does any device need full-duplex. The answers determine your wiring topology.

Mixing SPI modes on one bus is possible but painful. Changing CPOL/CPHA requires de-asserting all CS lines, reconfiguring the SPI peripheral, and re-asserting the target CS. If you have both a Mode-0 sensor and a Mode-3 EEPROM, consider whether a second SPI peripheral (most mid-range MCUs have two to four) is simpler than mode-switching logic.

Common debugging patterns

SPI problems almost always fall into one of five categories. Knowing which symptoms point to which cause saves hours at the logic analyser.

All reads return 0x00 or 0xFF

The slave's MISO line is not driven. Either CS̄ is never asserted (check your GPIO direction and polarity), the slave needs a power sequence or enable pin toggled before it outputs data, or the SPI mode is wrong and the slave is not interpreting commands. With a logic analyser, confirm CS̄ goes low, SCLK toggles, and MISO shows something other than a flat line.

First byte correct, subsequent bytes garbled

Classic CPHA mismatch. The slave shifts data on the opposite edge from what you have configured. The first bit is sometimes coincidentally correct (held from before the transfer began), but subsequent bits are captured half a cycle early or late. Flip CPHA and re-test.

Data correct at low speed, corrupted above N MHz

Setup or hold timing violation. The slave needs more time between CS̄ assertion and the first clock, or between the last clock and CS̄ de-assertion. Check tCSS and tCSH in the datasheet and add delays. It could also be PCB signal integrity — scope the SCLK line at the slave's pin (not the master's) and look for ringing or slow edges.

DMA transfer corrupts data on H7/M7

Cache coherency. The CPU wrote data to a cached buffer, but DMA reads from SRAM before the cache line was flushed. Call SCB_CleanDCache_by_Addr((uint32_t *)buf, len) before starting the DMA, or place SPI DMA buffers in the .dma_buffers section mapped to a non-cacheable MPU region.

QSPI flash returns wrong data in memory-mapped mode

The flash was not correctly put into quad-enable mode before switching to memory-mapped reads. The Quad Enable bit in the flash's Status Register 2 must be set with a Write Enable → Write Status Register sequence, then verified with a Read Status Register. Without this, quad reads silently return garbage because the flash is still in single-line mode while the MCU is clocking four data lines.

Interview Questions

Interview Q & A — SPI

Q1. What do CPOL and CPHA actually control, and how do you determine the correct mode for a device?

CPOL (Clock Polarity) sets the idle state of SCLK: CPOL=0 means SCLK rests low, CPOL=1 means it rests high. CPHA (Clock Phase) controls which edge is the data-capture edge: CPHA=0 captures on the leading (first) edge, CPHA=1 captures on the trailing (second) edge.

To determine the correct mode, read the device datasheet timing diagram. Find the idle state of SCK before CS̄ asserts (gives CPOL), then find which edge has the "data valid" annotation (gives CPHA). Mode 0 (CPOL=0, CPHA=0) is correct for most sensors; Mode 3 (CPOL=1, CPHA=1) is its clock-inverted equivalent and equally common. Mode 1 and Mode 2 are rare in practice.

Q2. How does SPI daisy chaining work, and when can you NOT use it?

In a daisy chain, all slaves share one CS̄ line. MOSI connects to the first slave's data input; each slave's serial output feeds the next slave's input. One CS̄ assert transmits N × word_size bits; when CS̄ rises, each device latches the word that arrived at its input. Because data ripples through the chain, the master must transmit bytes in reverse order — the first byte sent ends up in the last device.

Daisy chaining fails for any device that must simultaneously return read data while receiving write data — ADCs, sensors, EEPROMs with status bytes. In those cases the DOUT is not a transparent pass-through of DIN; it carries independent information. Only use daisy chains with devices designed for it (shift registers, LED drivers, some DACs).

Q3. Why is SPI faster than I2C, and where does that speed advantage end?

SPI has no overhead: no start/stop bits, no address byte, no ACK/NAK bits. Every clock cycle carries data. I2C uses an open-drain bus with a pull-up resistor and a strict protocol overhead of approximately 18 bits per byte (start, address, ACK, data, ACK, stop). SPI is also full duplex — both sides exchange data simultaneously — whereas I2C is half duplex with explicit direction changes.

The speed advantage ends where signal integrity does. Without the open-drain constraint of I2C, SPI can run at the push-pull GPIO drive strength and speed of the silicon — tens or hundreds of MHz. In practice, PCB capacitance, trace length matching, and slave input frequency limits are the binding constraints. For very short ranges (chip-to-chip on the same board), SPI wins decisively. For long cables or large buses with many nodes, CAN or RS-485 (with their robust differential signalling) are more appropriate than raw SPI.

Q4. What is Quad-SPI and why does it exist? When would you use it over standard SPI?

QSPI uses four bidirectional data lines (IO0–IO3) during the data phase of a transfer instead of one. This delivers four bits per clock cycle — four times the throughput of standard SPI at the same clock frequency. OSPI extends this to eight lines.

QSPI exists primarily for execute-in-place (XIP) from external NOR flash. A Cortex-M7 at 400–480 MHz can stall waiting for instruction fetch if the flash bus cannot supply bytes fast enough. Standard SPI at 133 MHz gives ~16 MB/s; QSPI at 133 MHz gives ~66 MB/s — enough to sustain most firmware code paths without cache misses stalling the pipeline.

Use QSPI when: (1) your MCU needs to run code from external flash, (2) you are streaming large blocks of data from flash (audio, graphics) and raw transfer speed matters, or (3) you need the memory-mapped address space that QSPI peripherals provide. For ordinary sensor and peripheral communication, standard SPI at 1–40 MHz is perfectly adequate and simpler to design.

Q5. You are using DMA to transmit SPI data on a Cortex-M7 and getting corrupted output. What is the most likely cause and how do you fix it?

The most likely cause is D-cache coherency. The Cortex-M7 has a separate data cache that operates independently of the DMA controller. When the CPU writes a buffer in cached SRAM, the data may remain in the cache lines and never be flushed to actual SRAM before DMA reads it — so DMA transfers stale data.

There are three standard fixes. First, call SCB_CleanDCache_by_Addr((uint32_t *)buf, len) (CMSIS function) after filling the buffer and before starting the DMA. This writes dirty cache lines back to SRAM. Second, allocate DMA buffers in a non-cacheable memory region by configuring the MPU to mark that SRAM region as non-cacheable — the CPU and DMA then always see the same data without any explicit flush. Third, place the buffer in DTCM (Tightly Coupled Memory), which is bypassed by the cache and always coherent, though DMA access to DTCM requires peripheral DMA support for that memory region (not all STM32 peripherals support it). The MPU non-cacheable approach is the most robust general solution.

Q6. How do you add more SPI slaves than you have GPIO pins?

Three practical approaches, in order of complexity: Demultiplexer IC — a 74HC138 (3-to-8 decoder) converts 3 GPIO lines into 8 active-low CS outputs, giving you 8 slaves for the cost of 3 pins. Shift register — an 8-bit output shift register (74HC595, connected via SPI itself) gives 8 CS lines from 3 or 4 SPI signals; the trade-off is that asserting a CS requires a separate SPI transaction to clock out the CS pattern, adding latency before each main transfer. Daisy-chaining where suitable — if devices support it, this eliminates the CS count problem entirely at the cost of reduced flexibility and the byte-reversal complexity.

On heavily constrained designs, a second SPI peripheral (if the MCU has one) is often cleaner than any of the above — it adds zero CS management complexity and allows both buses to run simultaneously for doubled bandwidth.
