Topic 04 · HB6 · Serial & Field-Bus Communication Protocols

UART — Baud Rate, Framing & Interrupts

The oldest asynchronous serial protocol in embedded systems — one wire, no clock, agreed-upon timing — and still the first bus every MCU brings up. From the BRR calculation to interrupt-driven ring buffers and error flag recovery.

UART predates the microcontroller by over a decade. The protocol is almost absurdly simple: sender and receiver agree on a bit rate, and then the sender drives a line low to signal a start bit, clocks out the data bits, and releases the line high for the stop bit — no clock wire, no handshake, no addressing. Yet for point-to-point debug output, GPS receivers, Bluetooth modules, and host-MCU bridges, UART remains the default choice because it requires exactly two GPIO pins and a single register write to configure.

The simplicity is deceptive. Getting UART right in an interrupt-driven system requires understanding exactly when each status flag is set and cleared, what the baud rate divider formula actually does to your clock, and how the hardware's three-sample majority-vote receiver detects noise without a reference clock. This topic covers all of it from the register level up.

The UART frame

Every UART transmission is a frame: a self-contained unit of bits with a defined structure. The line idles high. The start bit — always a single logic zero — tells the receiver "a frame is beginning, start your counter." The data bits follow LSB first in standard UART. An optional parity bit comes next. One or two stop bits — always logic high — close the frame and give the receiver time to process the byte before the next start bit.

The receiver samples each bit three times and takes a majority vote — a single glitch on one sample does not corrupt the result.

Key Idea

The receiver has no clock reference. It locks onto the falling edge of the start bit, then samples the centre of each expected bit period using its own internal clock running at 16× (or 8×) the baud rate. Every bit gets three samples; two-of-three wins. This is why UART tolerates small clock frequency errors — typically ±2–3% across the whole link — but fails catastrophically at ±5% or more, when the accumulated timing drift puts the sample point outside the data eye.

Register map and bit definitions

UART peripherals across Cortex-M MCUs share a nearly identical register layout. The register names below match the common industry convention; verify offsets and bit positions in your MCU's reference manual before porting.

Cuart_driver.h — register map and bit definitions
/* Change UART_BASE to your MCU's USART peripheral address.
 * STM32F1 USART1: 0x40013800  |  STM32F4 USART1: 0x40011000
 * nRF52840 UARTE0: 0x40002000 |  RP2040  UART0:  0x40034000  */
#define UART_BASE   0x40011000UL

/* Register map — volatile dereference of (base + offset) */
#define UART_SR   (*(volatile uint32_t *)(UART_BASE + 0x00U))  /* Status Register      */
#define UART_DR   (*(volatile uint32_t *)(UART_BASE + 0x04U))  /* Data Register        */
#define UART_BRR  (*(volatile uint32_t *)(UART_BASE + 0x08U))  /* Baud Rate Register   */
#define UART_CR1  (*(volatile uint32_t *)(UART_BASE + 0x0CU))  /* Control Register 1   */
#define UART_CR2  (*(volatile uint32_t *)(UART_BASE + 0x10U))  /* Control Register 2   */
#define UART_CR3  (*(volatile uint32_t + 0x14U))  /* Control Register 3   */

/* --- CR1 bit positions ------------------------------------------ */
#define UART_CR1_RE     (1U <<  2)  /* Receiver Enable                      */
#define UART_CR1_TE     (1U <<  3)  /* Transmitter Enable                   */
#define UART_CR1_RXNEIE (1U <<  5)  /* RXNE Interrupt Enable                */
#define UART_CR1_TCIE   (1U <<  6)  /* Transmission Complete Interrupt      */
#define UART_CR1_TXEIE  (1U <<  7)  /* TXE Interrupt Enable                 */
#define UART_CR1_PS     (1U <<  9)  /* Parity Selection: 0=Even, 1=Odd      */
#define UART_CR1_PCE    (1U << 10)  /* Parity Control Enable                */
#define UART_CR1_M      (1U << 12)  /* Word length: 0=8-bit frame, 1=9-bit  */
#define UART_CR1_UE     (1U << 13)  /* USART Enable — set LAST              */

/* --- CR2 stop-bit field (bits [13:12]) -------------------------- */
#define UART_CR2_STOP_1 (0U << 12)  /* 1 stop bit  — standard               */
#define UART_CR2_STOP_2 (2U << 12)  /* 2 stop bits — slow or noisy links    */

/* --- SR status flags -------------------------------------------- */
#define UART_SR_PE    (1U << 0)  /* Parity Error   — wrong parity bit    */
#define UART_SR_FE    (1U << 1)  /* Framing Error  — no valid stop bit   */
#define UART_SR_NE    (1U << 2)  /* Noise Error    — majority vote fail  */
#define UART_SR_ORE   (1U << 3)  /* Overrun Error  — DR not read in time */
#define UART_SR_RXNE  (1U << 5)  /* RX Not Empty   — byte ready in DR    */
#define UART_SR_TC    (1U << 6)  /* Transmission Complete — shift empty  */
#define UART_SR_TXE   (1U << 7)  /* TX Empty       — DR free for next    */

/* Convenience mask: any error flag set */
#define UART_SR_ERR   (UART_SR_PE | UART_SR_FE | UART_SR_NE | UART_SR_ORE)

Baud rate — the BRR calculation

BRR is the one register that trips up almost every first-time UART bringup. The formula is deceptively simple: divide the peripheral clock by the desired baud rate. The subtlety is rounding — integer truncation introduces a systematic error that grows at high baud rates relative to slow peripheral clocks. Adding half the denominator before dividing rounds to the nearest integer instead, cutting the maximum error roughly in half.

Cuart_driver.h — baud rate macro with rounding
/* UART_BRR_CALC — compute BRR register value for 16× oversampling.
 *
 * Formula: BRR = fPCLK / baud
 * Rounding: adding (baud/2) before dividing rounds to nearest integer,
 *           reducing the baud-rate error compared to plain truncation.
 *
 * Example calculations:
 *   9600 baud  @ 16 MHz : BRR = (16000000 + 4800)   / 9600   = 1667  (0x0683)
 *   115200 baud@ 16 MHz : BRR = (16000000 + 57600)  / 115200 = 139   (0x008B)
 *   9600 baud  @ 72 MHz : BRR = (72000000 + 4800)   / 9600   = 7501  (0x1D4D)
 *   115200 baud@ 72 MHz : BRR = (72000000 + 57600)  / 115200 = 626   (0x0272)
 *   115200 baud@ 48 MHz : BRR = (48000000 + 57600)  / 115200 = 417   (0x01A1)
 *
 * Actual baud error after rounding is typically < 0.5% — within the
 * ±2% tolerance most UART receivers require for reliable operation.    */
#define UART_BRR_CALC(fclk, baud)  (((fclk) + ((baud) / 2U)) / (baud))

Common Mistake

Using the wrong clock source. USART peripherals on many MCUs can be clocked from either APB1 or APB2 (or a dedicated USART clock domain on newer parts), and those buses often run at different frequencies. If your BRR calculation uses 72 MHz but the USART peripheral is on APB1 running at 36 MHz, the actual baud rate will be half what you expect — and every frame will be a framing error on the other end. Always confirm the peripheral clock source from the RCC configuration before computing BRR.

UART initialisation

Initialisation order matters. CR1 must be written while the peripheral is disabled (UE=0), because changing word length or parity while the peripheral is active produces unpredictable frame corruption. The BRR register also must be set before UE is asserted. The correct sequence is: clear everything, set BRR, set CR2 for stop bits, set CR1 with TE and RE, then set UE last.

Cuart_driver.c — UART_Init
#include "uart_driver.h"

/* UART_Init — configure for 8N1 at the requested baud rate.
 * fclk: peripheral clock in Hz (confirm APB1 vs APB2 for your MCU)
 * baud: desired baud rate (e.g. 9600, 115200, 1000000)
 *
 * Prerequisites — before calling:
 *   1. Enable the UART peripheral clock via RCC (MCU-specific)
 *   2. Configure TX pin as push-pull AF output
 *   3. Configure RX pin as input (floating or pull-up)             */
void UART_Init(uint32_t fclk, uint32_t baud)
{
    /* Step 1: Disable peripheral — required before changing CR1 fields.
     * Writing to M, PCE, PS while UE=1 produces undefined behaviour.  */
    UART_CR1 = 0;
    UART_CR2 = 0;
    UART_CR3 = 0;

    /* Step 2: Set baud rate divider.
     * BRR = fclk / baud (with rounding). For 16× oversampling the
     * hardware samples each bit at positions 7, 8, 9 of the 16 sub-clocks
     * and takes the majority. BRR written before UE is asserted.       */
    UART_BRR = UART_BRR_CALC(fclk, baud);

    /* Step 3: 1 stop bit — the 8N1 default.
     * 2 stop bits (UART_CR2_STOP_2) are used for RS-232 links or when
     * the receiver needs extra time to process bytes (slow UART-to-USB). */
    UART_CR2 = UART_CR2_STOP_1;

    /* Step 4: Enable TX and RX, then enable the peripheral last.
     * Setting TE causes an idle frame (all 1s) to be sent first — this
     * initialises the TX shift register and brings the line to a known
     * idle-high state before any real data goes out.
     * CR1.M=0 (8-bit), CR1.PCE=0 (no parity) remain cleared = 8N1.   */
    UART_CR1 = UART_CR1_TE            /* enable transmitter */
             | UART_CR1_RE            /* enable receiver    */
             | UART_CR1_UE;           /* enable peripheral  */
}

Polling transmit and receive

The polling model is the right starting point: no interrupts, no buffers, just wait-and-write. It works reliably for debug output and simple command-response protocols where you control both ends. Two flags govern polling: TXE tells you the data register is empty and safe to load the next byte; RXNE tells you the shift register has assembled a complete frame and copied it into the data register, ready to read.

Cuart_driver.c — polling transmit and receive
/* UART_SendByte — blocking polled transmit.
 *
 * TXE=1 means DR has been copied to the shift register.
 * The shift register is now clocking the previous byte out on the wire
 * while DR is free to accept the next one — hardware double-buffering.
 *
 * IMPORTANT: do NOT wait for TC (Transmission Complete) here.
 * TC goes high only after the LAST stop bit leaves the wire. Waiting for
 * TC between every byte would idle the transmitter for a full bit-period
 * between bytes, halving your effective throughput. Use TC only when you
 * need to know the wire is truly quiet (e.g. RS-485 direction change).  */
void UART_SendByte(uint8_t b)
{
    while (!(UART_SR & UART_SR_TXE));   /* wait: DR empty, safe to load  */
    UART_DR = (uint32_t)b;               /* write starts the frame        */
}

/* UART_ReadByte — blocking polled receive.
 *
 * RXNE=1 means the shift register has assembled a complete 8-bit frame
 * (start bit consumed, stop bit verified) and moved it to DR.
 * Reading DR clears RXNE automatically.
 *
 * This is the simplest possible RX path. In production, always check
 * UART_SR_ERR before reading DR — see the error handling section.      */
uint8_t UART_ReadByte(void)
{
    while (!(UART_SR & UART_SR_RXNE));  /* wait: byte assembled in DR    */
    return (uint8_t)UART_DR;             /* read clears RXNE              */
}

/* UART_SendString — transmit null-terminated string */
void UART_SendString(const char *s)
{
    while (*s) UART_SendByte((uint8_t)*s++);
}

/* UART_SendBuffer — transmit raw bytes of known length */
void UART_SendBuffer(const uint8_t *buf, uint32_t len)
{
    while (len--) UART_SendByte(*buf++);
}
TXE vs TC — interview classic

TXE (TX Empty) means the data register has been transferred to the shift register — DR is ready for the next byte, but the current byte is still being clocked out on the wire. TC (Transmission Complete) means the shift register is empty and the stop bit of the last frame has left the wire. For continuous streaming use TXE; for RS-485 where you must switch the transceiver direction after the last bit, wait for TC. Confusing the two is one of the top UART interview mistakes.

Interrupt-driven RX with ring buffer

Polling RXNE is fine when your main loop runs faster than one byte-period. At 115200 baud, a byte arrives every 87 µs. If any part of your main loop takes longer than that — an I2C transaction, an ADC conversion, a flash write — you miss the byte and the hardware flags an overrun error. An RX interrupt fires the instant RXNE goes high, stashes the byte in a ring buffer in microseconds, and lets the main loop drain the buffer at leisure.

Cuart_driver.c — interrupt-driven RX with circular buffer
/* Ring buffer — power-of-2 size lets us use a bitmask instead of modulo.
 * Modulo (%) is slow on MCUs without a hardware divider (e.g. Cortex-M0). */
#define RX_BUF_SIZE  64
#define RX_BUF_MASK  (RX_BUF_SIZE - 1)   /* works iff RX_BUF_SIZE is 2^N */

static volatile uint8_t  rx_buf[RX_BUF_SIZE];
static volatile uint32_t rx_head = 0;   /* ISR writes here (producer)  */
static volatile uint32_t rx_tail = 0;   /* main loop reads here (consumer) */

/* UART_EnableRxInterrupt — arm the RXNEIE bit so the CPU is woken on
 * every received byte. Also enable the NVIC IRQ for your UART instance
 * (NVIC_EnableIRQ(USART1_IRQn) — MCU-specific).                      */
void UART_EnableRxInterrupt(void)
{
    UART_CR1 |= UART_CR1_RXNEIE;       /* RXNE fires the IRQ            */
}

/* ISR — rename to match your MCU's UART interrupt vector symbol.
 *
 * Design rules for UART ISRs:
 *   1. Read SR first, then DR — this is the mandatory clear sequence.
 *   2. Keep it short: store the byte and exit. No processing in the ISR.
 *   3. If the buffer is full, drop the byte rather than blocking.
 *   4. volatile on rx_head/rx_tail prevents the compiler from caching
 *      them in registers across ISR boundaries.                        */
void UART_IRQHandler(void)
{
    uint32_t sr = UART_SR;              /* snapshot SR once              */

    if (sr & UART_SR_ERR) {
        (void)UART_DR;                  /* read DR clears FE/ORE/NE     */
        return;
    }

    if (sr & UART_SR_RXNE) {
        uint8_t b = (uint8_t)UART_DR;    /* reading DR clears RXNE       */
        uint32_t next = (rx_head + 1) & RX_BUF_MASK;
        if (next != rx_tail) {          /* buffer not full — store byte */
            rx_buf[rx_head] = b;
            rx_head = next;
        }
        /* if next == rx_tail: buffer full, byte silently dropped        */
    }
}

/* UART_ReadBuffered — main-loop consumer (non-blocking).
 * Returns 1 and writes *out if a byte is available, 0 if empty.
 * Safe to call from main loop without disabling interrupts because
 * rx_tail is only modified here and rx_head is only modified in the ISR. */
int UART_ReadBuffered(uint8_t *out)
{
    if (rx_tail == rx_head) return 0; /* empty                         */
    *out = rx_buf[rx_tail];
    rx_tail = (rx_tail + 1) & RX_BUF_MASK;
    return 1;
}

Error handling — FE, ORE, NE

The UART status register contains four error flags that latch independently. They are sticky — once set, they remain set until explicitly cleared. The clear sequence on most MCUs is: read SR, then read DR. Reading DR without first reading SR does not clear the flags. Skipping error handling means stale error flags eventually corrupt valid reads.

Error flag summary — SR bits [3:0] Bit Flag Name Cause Recovery ────────────────────────────────────────────────────────────────── [0] PE Parity Error Received parity bit doesn't Read SR, read DR match computed parity over data bits. Check baud + parity config [1] FE Framing Error No valid stop bit detected Read SR, read DR at expected position after data bits. → Wrong baud rate? → Sender uses 2 stop bits? [2] NE Noise Error 3-sample majority vote Read SR, read DR was not unanimous (2-of-3 won, not 3-of-3). Byte may still be valid. Indicates marginal signal quality. Check PCB trace length. [3] ORE Overrun Error New byte completed shifting Read SR, read DR before DR was read — old byte is LOST, PREVIOUS byte is gone. DR now holds the NEW (overrunning) byte. Use interrupt-driven RX.
Cuart_driver.c — UART_ReadWithErrorCheck
/* Error return codes */
#define UART_OK           0
#define UART_ERR_OVERRUN  1
#define UART_ERR_FRAMING  2
#define UART_ERR_NOISE    3
#define UART_ERR_PARITY   4
#define UART_ERR_NODATA   5

/* UART_ReadWithErrorCheck — non-blocking receive with full error handling.
 *
 * Clear sequence (mandatory on most MCUs):
 *   1. Read SR  — snapshots all flags
 *   2. Read DR  — clears RXNE and the sticky error flags simultaneously
 *
 * Skipping step 1 and going straight to DR leaves FE/ORE/NE latched,
 * so they will incorrectly flag the NEXT valid read.                  */
int UART_ReadWithErrorCheck(uint8_t *out)
{
    uint32_t sr = UART_SR;              /* Step 1: read SR first         */

    if (sr & UART_SR_ORE) {
        /* Overrun: the old byte was lost. DR holds the NEW byte.
         * Recovering: read DR to clear ORE, then decide whether
         * to keep the new byte or report the error and discard.       */
        (void)UART_DR;                  /* Step 2: clear the flag        */
        return UART_ERR_OVERRUN;
    }
    if (sr & UART_SR_FE) {
        /* Framing error: no stop bit where expected.
         * Most common cause: baud rate mismatch between the two ends.
         * Also triggered by a BREAK condition (sender holds line low). */
        (void)UART_DR;
        return UART_ERR_FRAMING;
    }
    if (sr & UART_SR_NE) {
        /* Noise error: the 3-sample majority vote was 2-1 rather than 3-0.
         * The byte in DR may still be correct — NE indicates degraded
         * signal quality, not necessarily a wrong bit. Log it and decide
         * at the application level whether to keep or discard.        */
        (void)UART_DR;
        return UART_ERR_NOISE;
    }
    if (sr & UART_SR_PE) {
        (void)UART_DR;
        return UART_ERR_PARITY;
    }
    if (sr & UART_SR_RXNE) {
        *out = (uint8_t)UART_DR;          /* Step 2: read clears RXNE     */
        return UART_OK;
    }
    return UART_ERR_NODATA;              /* RXNE not set — nothing ready  */
}
Overrun Recovery — Critical Detail

When ORE is set, the byte that caused the overrun is in DR — the byte you failed to read in time is gone forever. Reading DR clears ORE. On some MCU families (STM32L, STM32H, STM32G series) the error flags are cleared via a dedicated ICR (Interrupt Clear Register) register write rather than the SR→DR read sequence. Always check your reference manual's "Error flag clearing procedure" section — using the wrong sequence leaves flags latched and corrupts subsequent reads.

RS-485 half-duplex direction control

Standard UART is full-duplex: TX and RX on separate wires. RS-485 is a differential, half-duplex variant where a single twisted pair carries both directions, arbitrated by a direction-enable (DE) pin on the transceiver IC. Before transmitting, the MCU must assert DE to switch the transceiver to driver mode. After the last bit has left the wire — TC=1, not TXE=1 — the MCU de-asserts DE to return to receive mode. Many MCUs have a hardware DE output option that automates this; without it, the sequence must be managed manually in software.

Crs485.c — manual DE pin control for RS-485 half-duplex
/* Assumes DE pin is a GPIO output. Assert before first byte,
 * wait for TC after last byte, then de-assert.
 * Using TXE instead of TC here would release DE while the last
 * stop bit is still being clocked out — corrupting the frame.  */
void RS485_SendBuffer(const uint8_t *buf, uint32_t len)
{
    DE_Assert();                           /* switch to driver mode        */

    for (uint32_t i = 0; i < len; i++) {
        while (!(UART_SR & UART_SR_TXE));  /* wait for DR free             */
        UART_DR = buf[i];
    }

    /* Wait for TC=1: shift register has sent the last stop bit.
     * Only now is it safe to tri-state the driver.             */
    while (!(UART_SR & UART_SR_TC));

    DE_Deassert();                         /* return to receive mode       */
}
Interview Questions

Interview Q & A — UART

Q1. How does a UART receiver synchronise to incoming data without a clock signal?

The receiver locks onto the falling edge of the start bit — the line transitioning from idle-high to logic zero. From that moment it starts counting sub-clock intervals using its internal clock, which runs at 16× (or 8×) the agreed baud rate. Each bit period is divided into 16 sub-clocks; the receiver samples the line at sub-clocks 7, 8, and 9 and takes a 2-of-3 majority vote. This three-sample strategy means a single glitch that hits exactly one sample does not corrupt the bit decision.

The consequence is that both sides must agree on baud rate to within roughly ±2–3%. Beyond that threshold, the accumulated timing drift moves the sample window outside the data eye and errors multiply rapidly. There is no correction mechanism — if the clocks diverge, communication fails silently (framing errors) until you reconfigure one side.

Q2. What is the difference between the TXE and TC flags? Which do you use for continuous streaming, and which for RS-485?

TXE (Transmit Data Register Empty) goes high when the CPU-writable data register has been transferred to the hardware shift register. The shift register is now clocking out the current byte while DR is ready for the next one — this is the hardware's double-buffering mechanism. TXE goes high before the current byte has finished transmitting.

TC (Transmission Complete) goes high only after the shift register has clocked out the last bit of the last stop bit. The wire is truly idle.

For continuous byte streaming, wait on TXE — it keeps the shift register fed without gaps. For RS-485 direction switching, you must wait on TC before de-asserting the driver-enable pin, because the last stop bit is still on the wire when TXE goes high. Using TXE for RS-485 direction control truncates the last stop bit and produces a framing error at the far end.

Q3. Explain the overrun error (ORE). What is lost, what is in DR after ORE is set, and how do you recover?

ORE fires when the shift register completes assembly of a new byte while DR still holds the previous byte — the CPU did not read DR fast enough. The previous byte is permanently lost; it was overwritten when the shift register transferred the new byte to DR. DR now holds the new (overrunning) byte.

Recovery on most MCUs requires reading SR first, then reading DR. The SR→DR sequence clears the ORE flag. If you only read DR without reading SR, ORE remains set and will corrupt the next valid read check. On STM32L/H/G series, ORE is instead cleared by writing to a dedicated ICR (Interrupt Clear Register) — always verify the clearing procedure in your reference manual.

Prevention is better than recovery: use interrupt-driven RX with a ring buffer so that every byte is read from DR within microseconds of RXNE firing, long before the next frame can arrive even at 1 Mbit/s.

Q4. How do you calculate the BRR register value, and what goes wrong if you don't round the result?

For 16× oversampling: BRR = fPCLK / baud. Since both operands are integers, plain division truncates. The truncation error is at most one ULP (one BRR unit), which corresponds to a baud rate error of up to baud / fPCLK × 100%. At 115200 baud on a 16 MHz clock, BRR = 138.8 — truncating gives 138, which yields an actual baud rate of 115 942 — 0.64% fast, above the ±0.5% recommendation for robust links.

The fix is to round: BRR = (fPCLK + baud/2) / baud. Adding half the denominator before dividing rounds to the nearest integer, cutting the maximum error to ±0.5 ULP. At 115200 / 16 MHz this gives 139, for an actual rate of 115 108 — only 0.08% slow, well within tolerance. Always use the rounding form in production code.

Q5. Why is interrupt-driven RX safer than polling for most real-world applications?

Polling requires the CPU to visit the RXNE flag check faster than one byte-period to avoid overrun. At 115200 baud that window is 87 µs. Any single operation longer than that — a blocking I2C transaction, a flash erase, a long ISR for another peripheral — misses the byte. In a system with multiple peripherals and an RTOS, guaranteeing a 87 µs polling interval everywhere is impractical.

Interrupt-driven RX decouples byte arrival from CPU availability. The ISR fires within a few instruction cycles of RXNE going high, stores the byte in a ring buffer in O(1) time, and exits. The main loop drains the buffer whenever it gets scheduled. The only failure mode is a buffer overflow if the main loop falls behind for longer than the buffer can absorb — which is easily calculated: a 64-byte buffer at 115200 baud buys 5.5 ms of slack, which is sufficient for all but the most extreme real-time tasks.

Q6. What does the noise error (NE) flag mean, and is the byte in DR still usable when NE is set?

NE indicates that during the three-sample majority vote on one or more bits, the vote was 2-1 rather than 3-0. The hardware still accepted the 2-vote result as the bit value — the byte was not rejected — but the disagreement among samples is a warning that the signal quality is marginal.

Unlike a framing or overrun error, NE does not necessarily mean the byte is wrong. If a single glitch hit exactly one of the three samples, the majority vote still got the right answer. Whether to use or discard the byte depends on the application: for a debug console you might log the NE and keep the byte; for a safety-critical command channel you would discard it and request a retransmit. NE recurring frequently on a link is diagnostic: it points to impedance mismatch, excessive trace length, or ground potential difference between sender and receiver — all PCB-level problems, not software ones.
