Programmer's Model & Register File

Sixteen 32-bit registers, three special registers, two stacks, and one calling convention. Once you can read this map fluently, every disassembly listing tells you a story.

Every assembly listing, every HardFault dump, every debugger stack trace is written in the language of the Cortex-M programmer's model. This topic gives you fluency in that language: the sixteen general-purpose registers, the special-purpose registers that the compiler does not touch but you absolutely will, the two stack pointers, and the AAPCS calling convention that ties them all together.

Read this once and the next time GDB drops you into a backtrace at R7, you'll know what that means without thinking.

The register file — sixteen 32-bit registers

Every Cortex-M core has sixteen 32-bit general-purpose registers, named R0 through R15. Twelve of them are genuinely general purpose. The last four have hardware-assigned roles you cannot escape.

Cortex-M General-Purpose Register File ┌──────────┬──────────────────────────────────────────────┐ │ R0 │ Argument 1 / Return value 1 │ │ R1 │ Argument 2 / Return value 2 │ │ R2 │ Argument 3 │ │ R3 │ Argument 4 │ │ R4 │ Local variable (callee-saved) │ │ R5 │ Local variable (callee-saved) │ │ R6 │ Local variable (callee-saved) │ │ R7 │ Local variable (callee-saved) / frame ptr │ │ R8 │ Local variable (callee-saved) │ │ R9 │ Local variable (callee-saved) │ │ R10 │ Local variable (callee-saved) │ │ R11 │ Local variable (callee-saved) / frame ptr │ │ R12 IP │ Intra-Procedure scratch │ │ R13 SP │ Stack Pointer (MSP or PSP) │ │ R14 LR │ Link Register (return address) │ │ R15 PC │ Program Counter (next instruction to fetch)│ └──────────┴──────────────────────────────────────────────┘

The aliases at the bottom matter:

  • R13 = SP (Stack Pointer). Push and pop instructions implicitly modify this. There are actually two stack pointers in hardware (MSP and PSP) — covered below.
  • R14 = LR (Link Register). When a BL (branch with link) instruction executes, the return address is written to LR. Function epilogues do BX LR to return.
  • R15 = PC (Program Counter). Points to the instruction being fetched, which in Thumb mode is always two ahead of what is executing. The PC always has the Thumb-state bit (bit 0) set on any branch destination.
Key Idea

In Thumb-2, the PC reads as the address of the currently executing instruction plus 4. This is the "pipeline disclosure" effect — the CPU has already fetched two ahead. Code that does PC-relative addressing must account for this offset, and it is one of the most common surprises when reading hand-written assembly.

The special registers

Beyond the sixteen named registers, the M-profile architecture defines a handful of special-purpose registers reachable only via the MSR and MRS instructions (Move to/from Special Register). You will see these in fault handlers, RTOS context switches, and any time you read a debugger dump.

xPSR — the Program Status Register family

What looks like a single PSR is actually three overlapping views into one register: APSR, IPSR, and EPSR. The combined view is xPSR.

31 30 29 28 27 26 ... 16 15 ... 10 9 ... 0 ┌──┬──┬──┬──┬──┬─────────┬───────────────┬────────┐ │N │Z │C │V │Q │ ICI │ T-bit etc │ IPSR │ │ │ │ │ │ │ /IT │ (EPSR) │ excpt# │ └──┴──┴──┴──┴──┴─────────┴───────────────┴────────┘ └─── APSR ───┘ └ IPSR ┘ (flags) (which exception we're in)

What each piece does:

  • APSR (Application PSR). The four classic condition flags: Negative, Zero, Carry, oVerflow. Plus Q (saturation) when DSP extension is present. These are what conditional branches test.
  • IPSR (Interrupt PSR). Bottom 9 bits hold the exception number currently being serviced. Zero means thread mode (not in an exception). 1 is Reset, 2 is NMI, 3 is HardFault, and so on up to 16 + n for IRQ n.
  • EPSR (Execution PSR). Contains the T-bit (always 1 in Thumb-2; clearing it triggers a UsageFault) and the IT (If-Then) block state for conditional execution.

PRIMASK, FAULTMASK, BASEPRI — interrupt control

Three special registers control which interrupts can preempt the current execution. Together they form the interrupt-masking system, and understanding them is how you write critical sections that actually work.

RegisterWidthWhat it does
PRIMASK1 bitWhen set, disables all configurable-priority exceptions (everything except NMI and HardFault).
FAULTMASK1 bitWhen set, disables all exceptions including HardFault. NMI still gets through. Auto-cleared on exception return.
BASEPRI8 bitsDisables all exceptions with priority numerically greater than or equal to BASEPRI (i.e. less urgent). 0 means disabled. Cortex-M3 and up.

The CMSIS intrinsics that wrap these are:

Ccritical_section.c
#include "cmsis_gcc.h"

/* Crude: disable ALL interrupts (except NMI / HardFault).
 * Use only for the shortest possible windows. */
void critical_crude(void)
{
    uint32_t primask = __get_PRIMASK();
    __disable_irq();              /* CPSID i  →  PRIMASK = 1 */

    /* ...critical work... */

    __set_PRIMASK(primask);       /* restore — preserves nesting */
}

/* Surgical: keep high-priority IRQs (e.g. motor PWM) alive
 * while blocking only mid/low priority. */
void critical_surgical(void)
{
    uint32_t basepri = __get_BASEPRI();
    __set_BASEPRI(0x40);          /* block priority >= 0x40 */

    /* ...critical work...
     * Priority 0x00-0x3F can still preempt us.  */

    __set_BASEPRI(basepri);
}
Gotcha

BASEPRI uses raw priority values — the actual bits the NVIC compares — not the logical priorities you usually pass to NVIC_SetPriority(). If your silicon implements 4 priority bits (the common case), priorities are stored in the upper 4 bits of a byte: priority 5 is encoded as 0x50. Setting BASEPRI = 5 when you meant priority 5 will block almost everything by accident.

CONTROL — privilege and stack selection

The CONTROL register has just three bits but they decide major things:

bit 0 nPRIV 0 = privileged, 1 = unprivileged (thread mode only) bit 1 SPSEL 0 = use MSP, 1 = use PSP (thread mode only) bit 2 FPCA 1 = FPU context active (auto-set by FPU instruction)

After reset, the CPU is in thread mode, privileged, using the MSP. An RTOS will typically flip SPSEL to 1 once it has started a task, so each task runs on its own PSP-based stack while the kernel ISRs continue to use MSP. Privilege drops only if you explicitly call __set_CONTROL() to set nPRIV — useful for sandboxing untrusted task code behind an MPU.

The two stacks — MSP and PSP

Cortex-M has a dual-stack design that confuses beginners but turns out to be exactly the right abstraction for an RTOS.

Two Stack Pointers, One Cortex-M ┌──────────────────────────────────────────────────────┐ │ THREAD MODE │ │ (normal application code, can use either stack) │ │ │ │ CONTROL.SPSEL = 0 → uses MSP │ │ CONTROL.SPSEL = 1 → uses PSP │ └──────────────────────────────────────────────────────┘ │ │ (exception fires) ▼ ┌──────────────────────────────────────────────────────┐ │ HANDLER MODE │ │ (always uses MSP, regardless of SPSEL) │ │ │ │ The hardware always pushes the exception frame │ │ onto whichever stack thread mode was using, then │ │ switches to MSP for the handler. │ └──────────────────────────────────────────────────────┘ Layout in memory: ┌────────────────────┐ high address │ MSP grows down │ │ │ └────────────────────┘ │ │ ┌────────────────────┐ │ PSP grows down │ │ │ └────────────────────┘ low address

A bare-metal program with no RTOS uses MSP for everything. An RTOS hands each task its own PSP — when a context switch happens, the kernel saves the task's PSP value, loads the next task's PSP, and execution resumes seamlessly. The kernel itself, including all ISRs, runs on MSP, so RTOS code never has to worry about stack-overflowing a tiny user task.

The AAPCS — how functions actually call each other

AAPCS — ARM Architecture Procedure Call Standard — is the contract between caller and callee. The C compiler always follows it. Hand-written assembly must follow it to interoperate with C. Stack unwinding, fault forensics, and RTOS context switching all rely on it being followed correctly.

Argument passing

The first four arguments to a function go in R0–R3. Anything beyond that goes on the stack. Return value is in R0 (or R0:R1 for a 64-bit return).

C / ARM Asmaapcs_demo.c
/* C source */
int32_t compute(int32_t a, int32_t b, int32_t c, int32_t d,
                int32_t e, int32_t f)
{
    return a + b + c + d + e + f;
}

/* Compiles approximately to:
 *
 *   compute:
 *       ADD     R0, R0, R1      ; R0 = a + b
 *       ADD     R0, R0, R2      ; R0 += c
 *       ADD     R0, R0, R3      ; R0 += d
 *       LDR     R1, [SP, #0]    ; e from stack
 *       ADD     R0, R0, R1
 *       LDR     R1, [SP, #4]    ; f from stack
 *       ADD     R0, R0, R1
 *       BX      LR              ; return (value in R0)
 *
 * Note: a..d came in R0..R3.  e and f spilled to stack.
 *       Return value left in R0. */

Caller-saved versus callee-saved

This is the most useful AAPCS rule to memorise:

RegistersSaved byMeaning
R0–R3, R12, LRCallerIf you need their value after a function call, push them yourself.
R4–R11CalleeAny function that modifies these must restore them on exit.
SPBothMust be 8-byte aligned at any public function boundary.

Why the split? Caller-saved registers are scratch — fast to use, but they may be clobbered by any function call. Callee-saved registers are stable across calls — better for values you need across many statements.

The stacked exception frame

When any exception fires, the hardware automatically pushes eight registers onto the active stack before vectoring to the handler. This is the exception frame — and reading it is how you do fault forensics.

Exception Frame (low addr → high addr) (what the hardware pushes for you) SP after entry → ┌──────────┐ │ R0 │ ← argument 1 at time of fault ├──────────┤ │ R1 │ ← argument 2 ├──────────┤ │ R2 │ ← argument 3 ├──────────┤ │ R3 │ ← argument 4 ├──────────┤ │ R12 │ ├──────────┤ │ LR │ ← return address of faulting function ├──────────┤ │ PC │ ← address of the faulting instruction ├──────────┤ │ xPSR │ Pre-fault SP → └──────────┘ (if FPU active and lazy stacking off, 16 more words of S0-S15 + FPSCR follow)

When you stand in a HardFault handler and want to know which line of C code triggered the fault, you read PC out of this frame. The corresponding source line is decoded by your debugger or addr2line. Topic 03 of HB10 covers this forensic process in depth.

Test code — stack pointer and register inspection

This is a focused test routine you can drop into any project to verify the register file works as expected: it prints the live values of MSP, PSP, CONTROL, and the current stack pointer in use. Useful during RTOS bring-up and when investigating fault handlers.

Creg_inspect.c
#include <stdint.h>
#include <stdio.h>
#include "cmsis_gcc.h"

static uint32_t read_current_sp(void)
{
    uint32_t sp;
    __asm volatile ("mov %0, sp" : "=r" (sp));
    return sp;
}

void dump_registers(void)
{
    uint32_t msp     = __get_MSP();
    uint32_t psp     = __get_PSP();
    uint32_t control = __get_CONTROL();
    uint32_t primask = __get_PRIMASK();
    uint32_t ipsr    = __get_IPSR();
    uint32_t sp_now  = read_current_sp();

    printf("MSP       = 0x%08lX\n", msp);
    printf("PSP       = 0x%08lX\n", psp);
    printf("CONTROL   = 0x%08lX  (nPRIV=%u SPSEL=%u FPCA=%u)\n",
           control,
           (control     ) & 1,
           (control >> 1) & 1,
           (control >> 2) & 1);
    printf("PRIMASK   = %lu  (%s)\n",
           primask, primask ? "IRQ disabled" : "IRQ enabled");
    printf("IPSR      = %lu  (%s)\n",
           ipsr, ipsr ? "handler mode" : "thread mode");
    printf("SP-in-use = 0x%08lX\n", sp_now);
}

Expected output from thread mode on a bare-metal program with no RTOS:

ConsoleSWO output
MSP       = 0x20020F88
PSP       = 0x00000000        ← never been set; expected on bare metal
CONTROL   = 0x00000000        ← privileged, MSP, no FPU activity
PRIMASK   = 0  (IRQ enabled)
IPSR      = 0  (thread mode)
SP-in-use = 0x20020F88        ← same as MSP, as expected
When PSP looks wrong

If you ever see PSP set to 0xFFFFFFFF or some other obvious garbage on a system you thought was bare-metal, suspect that a stray __set_CONTROL call corrupted CONTROL.SPSEL. The hardware doesn't validate PSP at write time — it just blindly trusts the pointer at the next push.

Interview Questions

Interview Q & A — Register File

Q1. What does AAPCS stand for, and why do you care about it?

ARM Architecture Procedure Call Standard. It defines how arguments are passed, where return values live, which registers must be preserved across calls, and how the stack is aligned.

You care for three concrete reasons: stack unwinders (for fault decode and debugger backtraces) assume AAPCS is followed, hand-written assembly must conform to it to interoperate with C, and any RTOS context switch is essentially an AAPCS-compatible save and restore of the same set of registers.

Q2. Which registers are caller-saved and which are callee-saved on Cortex-M?

Caller-saved: R0–R3, R12, LR. The caller must save these before a call if it needs them afterwards.

Callee-saved: R4–R11. Any function that modifies these registers must save them on entry and restore them on exit. SP must be 8-byte aligned at function boundaries — that's also AAPCS.

This is why hand-written assembly typically begins with PUSH {R4-R11, LR} if it uses those registers, and ends with POP {R4-R11, PC}.

Q3. What is the difference between MSP and PSP, and when does each get used?

MSP — Main Stack Pointer — is the default. It is what the CPU comes up using after reset, and it is always used in handler mode (i.e. inside any exception or interrupt).

PSP — Process Stack Pointer — is optional. Thread mode can be configured to use it by setting CONTROL.SPSEL = 1. PSP exists primarily for RTOS use: each task gets its own PSP, so the kernel can switch tasks by swapping PSP values while keeping a single MSP for itself and all ISRs.

On a bare-metal program with no RTOS, PSP is never touched and effectively does not exist.

Q4. What is in the stacked exception frame, and why is it useful?

When any exception fires, the CPU automatically pushes 8 words onto the active stack: R0, R1, R2, R3, R12, LR, PC, xPSR. If the FPU was active and lazy stacking is off, S0–S15 and FPSCR are stacked too — that's 18 more words.

The frame is useful for two things. First, fault forensics: in a HardFault handler, the PC value in the frame tells you exactly which instruction faulted, which is how you find the C line that caused the fault. Second, RTOS context switching: a switching scheduler relies on this frame being there, so it only needs to save the additional R4–R11 manually — the hardware has done the rest.

Q5. What is the difference between PRIMASK and BASEPRI, and when would you use each?

PRIMASK is a single bit. When set, it disables every configurable-priority exception — every interrupt, every SysTick, everything except NMI and HardFault. It is sometimes called the "big hammer".

BASEPRI is an 8-bit threshold. It disables exceptions whose priority is numerically greater than or equal to (i.e. less urgent than) BASEPRI. So you can block low and mid priority interrupts while still letting a high-priority motor PWM interrupt through. BASEPRI exists on Cortex-M3 and up; it is not on M0/M0+.

Use PRIMASK for the very shortest critical sections (a few cycles updating a flag). Use BASEPRI for longer sections in real-time systems where some high-priority interrupts must continue to fire — for example, an RTOS critical section that protects scheduler state but keeps motor or audio ISRs alive.

Q6. If the PC always reads as the current instruction plus 4, how do PC-relative loads work in compiler-generated code?

The compiler accounts for the offset when it emits PC-relative load instructions like LDR R0, [PC, #20]. The "+4 pipeline disclosure" effect is well-defined: the PC value used by these instructions is always the address of the current instruction plus 4 (in Thumb-2). So when you read the assembly listing, that #20 displacement is measured from PC = current + 4, not from the instruction itself.

This bites people writing hand assembly. The classic gotcha is computing a literal pool offset by hand and being off by 4. Modern toolchains let you use a label and let the assembler do the arithmetic.

Q7. In CONTROL register, what does setting the nPRIV bit do, and why would you do it?

Setting CONTROL.nPRIV = 1 drops thread mode from privileged into unprivileged execution. Once unprivileged, the code cannot access privileged-only special registers (PRIMASK, BASEPRI, CONTROL itself), and any MPU regions marked privileged-only become inaccessible — touching them causes a MemManage fault.

You do this when running untrusted task code in an RTOS. The kernel keeps itself in privileged mode, and runs user tasks unprivileged behind an MPU. A bug or buffer overflow in a user task then traps cleanly instead of being able to corrupt the kernel or other tasks. This is the foundation of memory protection on Cortex-M without an MMU.
