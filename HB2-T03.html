Memory Map, Bus Matrix & AHB / APB

The 4 GB address space is the same on every Cortex-M ever made. What the silicon vendor wires into it is what makes the chip your chip.

Cortex-M defines a flat, byte-addressable 32-bit memory map — four gigabytes of address space, divided into eight one-gigabyte regions, each with a fixed purpose. Every Cortex-M chip ever shipped uses the same map. What changes from vendor to vendor is what is actually wired into each region: how much flash, how much SRAM, which peripherals at which addresses, and what bus fabric connects them.

Understanding this layout is the difference between firmware that "just works on STM32" and firmware that you can move between vendors with a single header file change.

The architectural memory map

The map is fixed by the architecture. The CPU itself treats each region according to its default memory type — Normal, Device, or Strongly-ordered — which affects caching, reordering, and access size rules.

Cortex-M Architectural Memory Map (4 GB) 0xFFFFFFFF ┌────────────────────────────┐ │ Vendor Specific │ System region 0xE0100000 ├────────────────────────────┤ (private peripherals, │ Private Peripheral Bus │ debug, vendor-defined) 0xE0000000 ├────────────────────────────┤ ← System, XN │ External Device 1 GB │ Off-chip peripherals 0xA0000000 ├────────────────────────────┤ ← Device, XN │ External RAM 1 GB │ SDRAM, external SRAM 0x60000000 ├────────────────────────────┤ ← Normal │ Peripheral 0.5 GB │ On-chip peripherals 0x40000000 ├────────────────────────────┤ ← Device, XN │ SRAM 0.5 GB │ Internal RAM 0x20000000 ├────────────────────────────┤ ← Normal │ Code 0.5 GB │ Flash, boot ROM 0x00000000 └────────────────────────────┘ ← Normal XN = "eXecute Never" — fetching code from this region triggers a UsageFault. Stops attackers running code in RAM/peripherals.
Key Idea

The default memory type matters even if you never touch the MPU. Writes to Device memory (peripheral region) are not buffered and not reordered — they always complete in the order you wrote them. Writes to Normal memory (SRAM, code) can be buffered and reordered by the bus fabric for performance. This is why volatile is necessary for peripheral access, and also why DMA buffers in cached SRAM need explicit cache maintenance on Cortex-M7.

The code region — 0x00000000 to 0x1FFFFFFF

This is where flash lives, where the vector table lives at reset, and where most executable code is fetched from. The first two words at 0x00000000 are mandatory:

  • 0x00000000 — initial value of MSP, loaded by hardware at reset
  • 0x00000004 — initial PC value, the address of Reset_Handler

A vendor can alias their physical flash anywhere they like inside the code region. Most STM32 parts map flash to both 0x00000000 (for the initial vector fetch) and 0x08000000 (the natural location). The "0x08" address is what you should always use in linker scripts — it survives boot mode changes, where the boot pins might remap 0x00000000 to ROM or system memory instead.

The SRAM region — 0x20000000 to 0x3FFFFFFF

Internal SRAM lives here. Stack, heap, .bss, .data — everything the linker assigns to "RAM" sits in this region. Cortex-M3 and M4 also include a bit-band alias subregion (0x22000000 onwards) that lets you atomically set or clear a single bit in the lowest megabyte of SRAM by writing to a calculated address. Removed in Cortex-M7 and later.

Bit-Band Aliasing (Cortex-M3 / M4 only) ┌──────────────────────────────────────────────────────────┐ │ Bit-band region: 0x20000000 - 0x200FFFFF (1 MB) │ │ Each bit in this region has its own 32-bit alias address │ │ in the alias region. │ ├──────────────────────────────────────────────────────────┤ │ Bit-band alias: 0x22000000 - 0x23FFFFFF (32 MB) │ │ Writing 0 or 1 to an alias address sets the target bit │ │ atomically — no read-modify-write cycle. │ └──────────────────────────────────────────────────────────┘ Alias address = 0x22000000 + (byte_offset_in_region * 32) + (bit_index * 4) Example: bit 3 of byte at 0x20000010 = 0x22000000 + (0x10 * 32) + (3 * 4) = 0x22000200 + 12 = 0x2200020C

The peripheral region — 0x40000000 to 0x5FFFFFFF

Memory-mapped peripherals live here. On most ARM-based MCUs, this region is the bridge between the CPU's AHB bus and the slower APB peripheral buses. The address layout inside this region is entirely vendor-defined — there is no architectural rule for where GPIO, UART, or SPI registers must sit.

Almost every Cortex-M architecture peripheral region exposes an APB1 segment (lower-speed, lower-power peripherals — TIM2, UART, I2C, etc.) and an APB2 segment (higher-speed peripherals — SPI, USART1, TIM1, ADC). The Reference Manual for the specific chip is the authoritative source.

The system region — 0xE0000000 and up

This is the most important region you have never thought about. It contains the Private Peripheral Bus (PPB) — every Cortex-M's built-in system registers, all sitting at architecturally fixed addresses:

AddressWhat lives there
0xE000E000 – 0xE000EFFFSystem Control Space (SCS): SCB, NVIC, SysTick, MPU
0xE0001000DWT — Data Watchpoint and Trace
0xE0002000FPB — Flash Patch and Breakpoint (M3/M4)
0xE0000000ITM — Instrumentation Trace Macrocell
0xE0040000TPIU — Trace Port Interface Unit
0xE000ED00SCB.CPUID — the part-identification register (Topic 01)
0xE000ED90MPU base (Topic 06)
0xE000ED08SCB.VTOR — Vector Table Offset Register (Topic 08)

These addresses are the same on every Cortex-M ever made. They are why CMSIS works without any vendor knowledge for the core itself.

The bus matrix — what actually connects everything

Inside the silicon, the CPU and peripherals are connected by a bus matrix built from AMBA (Advanced Microcontroller Bus Architecture) protocols. AMBA defines three main flavours: AHB (high-performance), APB (peripheral), and AXI (Cortex-M7 and applications processors). Each is a different trade-off between speed, area, and complexity.

I-bus, D-bus, S-bus

The Cortex-M3 and M4 split their CPU port into three buses. This is what allows the CPU to fetch an instruction from flash, load data from SRAM, and access a peripheral on the system bus all in the same cycle — the Harvard architecture advantage.

  • I-bus (Instruction bus) — fetches instructions from the code region (0x00000000–0x1FFFFFFF).
  • D-bus (Data bus) — loads/stores data from the code region too, when literal pools or constants are read.
  • S-bus (System bus) — everything else: SRAM, peripherals, PPB.

This is why constants placed in flash (.rodata) and code in flash (.text) can be accessed simultaneously: I-bus is reading the instruction, D-bus is reading the constant, and S-bus is doing something with SRAM. No contention.

AHB versus APB — speed versus complexity

AHB (Advanced High-performance Bus) runs at the full CPU clock. It supports burst transfers, pipelined access, and multiple bus masters (CPU, DMA controllers, Ethernet MAC). Used for memory, DMA, and high-bandwidth peripherals.

APB (Advanced Peripheral Bus) runs at a divided-down clock — typically half or quarter of the CPU. It is single-master, non-pipelined, and much smaller in silicon. Used for low-bandwidth peripherals where speed does not matter: UART, I2C, GPIO config, RTC.

An AHB-to-APB bridge sits between them. When the CPU accesses a peripheral register, the access goes through the bus matrix on AHB, hits the bridge, and is translated into a slower APB transaction. This is why peripheral reads take more cycles than you might expect — the bridge serializes the access.

AXI — the Cortex-M7 upgrade

Cortex-M7 replaces the older AHB-Lite interface with AXI (Advanced eXtensible Interface) for its main system bus. AXI is fully pipelined with separate address/read/write channels, supporting out-of-order completion. This is what lets the M7 sustain hundreds of MHz with caches and burst transfers from external SDRAM.

AHB-Lite AXI (M3/M4/M33) (M7, applications cores) ┌──────────┐ ┌──────────────────┐ │ Master │ │ Master │ └─┬─┬──┬──┬┘ └─┬──┬──┬───┬──┬──┬┘ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ ADDR DATA HSEL HRDY AR AW W R B BREADY (one transfer at a time) (independent channels, pipelined out-of-order)

The tightly coupled memories — TCMs

Cortex-M7 (and some M55/M85 implementations) adds two special memory blocks that sit outside the cache and outside the main bus matrix: ITCM (Instruction TCM) and DTCM (Data TCM). They are small SRAMs (typically 16 KB to 256 KB) wired directly to the CPU on dedicated buses.

Why this matters: an ITCM access has zero wait states and zero cache miss risk. Code placed in ITCM runs at full CPU speed deterministically — perfect for interrupt handlers and inner loops. DTCM is the same for data: zero-latency, no cache coherency issues, ideal for DMA buffers.

Linker Script Pattern

To place a hot function in ITCM, mark it with a custom section attribute and route that section in the linker script. The common pattern is __attribute__((section(".itcm_text"))) on the function definition, plus a matching SECTIONS rule in the .ld file mapping .itcm_text into the ITCM memory block. Covered in detail in HB4 Topic 03.

The same Cortex-M4 core on an NXP K66F or Microchip SAM4E has the same architectural memory map but completely different vendor addresses for these peripherals. This is why peripheral access code is the least portable part of any firmware project — the CPU is identical but the addresses are not.

Test code — memory map probe

This routine reads from each architectural region and confirms what is present. Useful during board bring-up to verify SRAM is mapped, peripherals respond, and the PPB is reachable.

Cmemmap_probe.c
#include <stdint.h>
#include <stdio.h>

/* Generic region samples — addresses tweaked per vendor. */
#define FLASH_BASE      0x08000000UL   /* STM32 main flash alias */
#define SRAM_BASE       0x20000000UL
#define PERIPH_BASE     0x40000000UL
#define PPB_CPUID      0xE000ED00UL
#define PPB_VTOR       0xE000ED08UL

static uint32_t safe_read(uint32_t addr)
{
    return *(volatile uint32_t *)addr;
}

void probe_memory_map(void)
{
    printf("--- Memory map probe ---\n");

    /* Flash: first 8 bytes hold initial MSP and Reset_Handler */
    printf("Flash[0]  (init MSP)     = 0x%08lX\n",
           safe_read(FLASH_BASE));
    printf("Flash[1]  (Reset_Handler) = 0x%08lX\n",
           safe_read(FLASH_BASE + 4));

    /* SRAM: read whatever happens to be at start of RAM */
    printf("SRAM[0]                   = 0x%08lX\n",
           safe_read(SRAM_BASE));

    /* PPB: CPUID must be readable on every Cortex-M */
    printf("PPB CPUID                 = 0x%08lX\n",
           safe_read(PPB_CPUID));

    /* PPB: VTOR tells us where vector table actually lives */
    printf("PPB VTOR                  = 0x%08lX\n",
           safe_read(PPB_VTOR));
}

Typical output on an STM32F4 with a vector table at the flash origin:

ConsoleSWO output
--- Memory map probe ---
Flash[0]  (init MSP)     = 0x20020000   ← stack starts at 128 KB into SRAM
Flash[1]  (Reset_Handler) = 0x080001C9   ← Thumb addr (LSB=1 mandatory)

Reading from unmapped regions causes faults

Accessing an address that the vendor has not wired up will trigger a BusFault (escalated to HardFault on most parts). The probe routine above only touches regions that must exist by architecture (PPB) or that you have already confirmed. Do not blindly read 0x60000000 or 0xA0000000 on a chip without external memory.

Interview Questions

Interview Q & A — Memory Map & Bus

Q1. Why does the Cortex-M place SRAM at 0x20000000 and peripherals at 0x40000000?

To give them different default memory types. SRAM at 0x20000000 is in the Normal memory region — the bus matrix can buffer, reorder, and cache accesses there for performance. Peripherals at 0x40000000 are in the Device region — accesses are strictly ordered, never reordered, and always reach the destination in the sequence the CPU issued them.

This is the architectural reason volatile matters for peripherals: even without it, the compiler might reorder accesses, but the bus matrix will not — the type protects you partially. Cached data, by contrast, requires explicit cache maintenance because the bus matrix freely reorders Normal accesses.

Q2. What is the difference between AHB and APB, and why do MCUs have both?

AHB runs at the full CPU clock, supports burst transfers and pipelined access, and supports multiple masters (CPU, DMA, Ethernet). It is bigger in silicon and used for memory and high-bandwidth peripherals.

APB runs at a divided-down clock (often half or quarter), is single-master, and is not pipelined. It is much smaller in silicon — perfect for low-bandwidth peripherals like UART or GPIO config registers.

Why both? Cost and power. Putting every peripheral on AHB would consume die area and power for no real benefit — a UART running at 115 kbaud does not need 168 MHz bus access. The AHB-to-APB bridge gets the slow peripherals onto a slow, small bus while still letting the CPU access them transparently.

Q3. What is bit-banding, when is it useful, and on which cores is it available?

Bit-banding is a hardware feature on Cortex-M3 and M4 that maps each bit in the lowest 1 MB of SRAM (and the lowest 1 MB of peripheral space) to a unique 32-bit address in an alias region. Writing 0 or 1 to that alias address atomically sets or clears the target bit — no read-modify-write cycle, no risk of being interrupted between the read and the write.

It is useful for race-free bit manipulation in interrupt-heavy code. Without bit-banding, setting a single bit in a flag register requires a read-modify-write, which can race with an ISR that touches the same byte.

Bit-banding was removed from Cortex-M7 and later because the LDREX/STREX atomic primitives provide a more general solution.

Q4. What are TCMs, and why does the Cortex-M7 have them when it already has caches?

TCM stands for Tightly Coupled Memory — two small SRAM blocks (ITCM for instructions, DTCM for data) wired directly into the CPU's pipeline, outside the cache hierarchy and outside the main bus matrix.

The reason for having both caches and TCMs: determinism. A cache gives you average-case performance but worst-case is bounded by the slowest memory you might miss into. For real-time code where worst-case latency matters — an interrupt handler that must complete in a known number of cycles, or an audio inner loop that cannot afford a cache miss — TCM provides single-cycle, predictable access.

The typical pattern is: bulk code and data live in flash/SRAM behind the cache; hot, latency-critical code goes in ITCM; DMA buffers and other latency-critical data go in DTCM.

Q5. Where is the Private Peripheral Bus and what lives in it?

The PPB starts at 0xE0000000 and contains everything the ARM core needs to function: the System Control Block (CPUID, VTOR, reset control), the NVIC (interrupt enable/priority registers), the SysTick timer, the MPU control registers, and the debug components (DWT, ITM, FPB, TPIU).

What makes it special is that the addresses are architecturally fixed — they are the same on every Cortex-M ever made, from M0 to M85. This is why CMSIS works portably for core access: SCB->CPUID always reads from 0xE000ED00, regardless of vendor.

The PPB is also Execute-Never by default — you cannot run code from 0xE000xxxx. The architecture enforces this to prevent attackers from putting shellcode in a memory-mapped register.

Q6. Why does the Cortex-M3/M4 have three CPU buses (I, D, S) instead of one?

To allow truly parallel access. With separate I-bus (instruction fetch from code region), D-bus (data load from code region — usually constants in flash), and S-bus (everything in SRAM, peripherals, and PPB), the CPU can:

Fetch an instruction from flash on the I-bus, load a constant from flash on the D-bus, and load a variable from SRAM on the S-bus — all in the same cycle. This is a Harvard architecture optimisation, and it is the reason simple loops on a Cortex-M4 can issue one instruction per cycle while still touching memory.

The Cortex-M7 collapses these into a single AXI master plus the TCM ports because AXI's pipelined out-of-order behaviour makes the explicit bus split unnecessary.
