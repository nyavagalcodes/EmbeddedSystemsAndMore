Processor Architectures Overview

Before you write a single register access, you need to know which Cortex you're talking to. The M-class and A-class lines descend from a common ARM ancestry but they solve fundamentally different problems — and the firmware that runs on each looks nothing alike.

The ARM family at a glance

ARM is not one processor. It is a sprawling family of architectures licensed to silicon vendors who integrate ARM cores into their own chips. For embedded engineers, three product lines matter:

  • Cortex-M — the microcontroller line. Tiny, deterministic, deeply integrated peripherals. Runs bare metal or a real-time operating system. This is where 90% of embedded firmware lives.
  • Cortex-A — the applications processor line. Runs Linux, Android, full operating systems. Has an MMU, caches, multiple cores. Powers your phone and your Raspberry Pi.
  • Cortex-R — the real-time line. Sits between M and A. Used in storage controllers, automotive ECUs, baseband modems. Most embedded engineers never touch one.

Inside Cortex-M there are several distinct cores, and the differences matter for what you can do with them.

The Cortex-M family compared

A few things to internalize from that table:

  • All Cortex-M cores execute Thumb-2 instructions (M0/M0+ run a subset). You will never write ARM 32-bit instructions for a Cortex-M. The 16-bit Thumb encoding with selected 32-bit instructions is what lives in flash.
  • The MPU is optional on M0+ and standard on M3 and up. If your firmware needs memory protection — process isolation, stack overflow detection — check the part number, not just the core family.
  • The FPU is optional even on M4 and M33. Silicon vendors decide whether to include it. STM32F407 has one, STM32F410 does not. Read the datasheet before you assume hardware float.
  • Cortex-M7 is superscalar. It can dispatch two instructions per cycle under the right conditions. This is why M7 chips post much higher CoreMark scores than M4 chips at the same MHz.

What Cortex-M shares

Every Cortex-M, from the M0 in a $0.20 sensor MCU to the M7 in a $20 industrial controller, shares an architectural backbone. Knowing that backbone gives you transferable skills across silicon vendors.

The fixed memory map is one of the cleverest decisions ARM made. Every Cortex-M, regardless of vendor, places the NVIC, SysTick, MPU, and SCB at the same addresses inside the Private Peripheral Bus region. That means CMSIS — the Cortex Microcontroller Software Interface Standard — works identically across all vendors. The code below is portable from STM32 to Nordic to NXP to TI without changes:

Cenable_systick.c
/* Enable SysTick to fire every 1 ms at 100 MHz CPU clock */
/* This code runs unchanged on any Cortex-M from any vendor */

#include "core_cm4.h"  /* CMSIS header, vendor-independent */

void systick_init(void) {
    SysTick->LOAD = 100000 - 1;           /* 100 MHz / 1 kHz */
    SysTick->VAL  = 0;
    SysTick->CTRL = SysTick_CTRL_CLKSOURCE_Msk
                  |  SysTick_CTRL_TICKINT_Msk
                  |  SysTick_CTRL_ENABLE_Msk;
}

Cortex-A — a different beast

Where Cortex-M is built for determinism and tight integration, Cortex-A is built for throughput and full-OS workloads. The differences cascade through every layer of the firmware stack.

AspectCortex-MCortex-A
Memory protectionMPU (region-based)MMU (page tables, virtual memory)
CachesOptional, simpleAlways, L1+L2 minimum
Exception modelNVIC, vectored, on-chip stackGIC, banked SP per mode
BootVector table at flash baseMulti-stage from ROM → BL1 → BL2 → kernel
Typical OSBare metal or RTOS (FreeRTOS, Zephyr)Linux, Android, QNX
RAMKB to a few MB on-chip SRAMGB of external DDR
Boot timeMillisecondsSeconds
Key Idea

An MMU translates virtual addresses to physical ones using page tables. An MPU only enforces access rules on physical regions. The MMU makes Linux possible; the MPU makes RTOS safety possible. Different problems, different solutions.

How to identify what core you're on

The CPUID register in the System Control Block tells you exactly what you're running on. Useful for portable firmware that needs to know whether the FPU exists or the DSP extension is present.

Cidentify_core.c
#include <stdio.h>
#include "core_cm4.h"

void identify_core(void) {
    uint32_t cpuid = SCB->CPUID;

    uint8_t  implementer = (cpuid >> 24) & 0xFF;
    uint8_t  variant     = (cpuid >> 20) & 0x0F;
    uint16_t partno      = (cpuid >> 4)  & 0xFFF;
    uint8_t  revision    =  cpuid        & 0x0F;

    /* implementer 0x41 = 'A' = ARM Limited                  */
    /* partno 0xC20 = M0, 0xC23 = M3, 0xC24 = M4, 0xC27 = M7 */
    printf("Core part: 0xC%X  rev: r%dp%d\n",
            partno, variant, revision);

    /* Check whether the FPU exists by reading CPACR  */
    uint32_t cpacr = SCB->CPACR;
    if ((cpacr >> 20) & 0xF)
        printf("FPU is present and enabled\n");
}

Interview Questions

Interview Question

What is the difference between Cortex-M and Cortex-A, and when would you choose one over the other?

Answer

Cortex-M is built for deterministic real-time control. It has an MPU (not an MMU), no virtual memory, on-chip flash and SRAM, a vectored interrupt controller (NVIC) with single-cycle entry, and is designed to run bare metal or a small RTOS. Boot time is microseconds. Power consumption is microamps in sleep.

Cortex-A is built for throughput and full operating systems. It has an MMU with page tables, L1 and L2 caches, a generic interrupt controller (GIC), runs out of external DDR RAM, and expects to boot Linux or Android. Boot time is seconds. Power consumption is hundreds of milliwatts even idle.

Choose Cortex-M when you need: hard real-time deadlines, low power, low cost, fast boot, deterministic interrupt latency. Choose Cortex-A when you need: a full OS, networking stacks, complex UI, multi-process isolation, gigabytes of memory, file systems.

Interview Question

Why does ARM use Thumb-2 instead of full 32-bit ARM instructions on Cortex-M?

Answer

Code density. Thumb-2 mixes 16-bit and 32-bit instructions, so common operations encode in 16 bits and you get roughly 30% smaller code than equivalent ARM-32 code. On a microcontroller with 64 KB or 128 KB of flash, that's massive — you fit more functionality per byte.

Cortex-M cores execute Thumb-2 exclusively. There's no ARM-32 state to switch into. This simplifies the silicon (no instruction set state bit to track) and saves power.

The trade-off — slightly fewer registers usable in 16-bit form, some encoding restrictions — doesn't matter for typical MCU workloads, which are dominated by load/store/branch and rarely benefit from the wider encoding.

Interview Question

An interviewer asks: "I have a part labeled STM32F407. Tell me everything you can infer about the core."

Answer

The "F4" series from STMicro uses Cortex-M4 with FPU (the "07" suffix in STM32 indicates higher-end variants with FPU; F401 also has FPU but F410 has the FPU as well — you have to read the datasheet, but F407 definitely has it).

From the Cortex-M4 designation we can infer:

  • Thumb-2 instruction set with DSP extensions (SIMD on 16-bit halves of 32-bit registers — useful for audio and motor control)
  • 3-stage pipeline, in-order execution
  • MPU is present (standard on M3 and up)
  • Single-precision FPU (IEEE 754 float, not double)
  • Memory map follows the standard Cortex-M layout — NVIC at 0xE000E100, SysTick at 0xE000E010
  • Maximum 240 external interrupts via NVIC (vendor-specific count; F407 implements 82)
  • Bit-banding regions at 0x22000000 and 0x42000000 for atomic single-bit access

For full specs — clock speed (168 MHz on F407), flash size, RAM, peripheral set — you still need the STM32F407 datasheet. But the core capabilities come from the Cortex-M4 architecture reference manual.

Interview Question

What does it mean for Cortex-M7 to be "superscalar"? Why does it matter?

Answer

Superscalar means the core can dispatch and execute more than one instruction per clock cycle. Cortex-M7 has dual-issue capability with a 6-stage pipeline. Under the right conditions — independent instructions, no register conflicts, predictable branches — it can sustain close to 2 instructions per cycle.

This is why an M7 at 400 MHz typically benchmarks at 2.5x to 3x the performance of an M4 at the same clock. The CoreMark score for Cortex-M7 is around 5.0 per MHz versus 3.4 for M4 — that's the superscalar effect.

It matters for high-throughput firmware: image processing, real-time audio, complex control algorithms, USB high-speed packet handling. It does not matter for simple control loops, where you're memory-bound or peripheral-bound anyway.

Note that the additional pipeline depth (6 stages vs 3 on M4) means a slightly higher interrupt latency — typically 12 cycles on M7 vs 12 on M4 due to architecture optimizations, but worst-case can be higher. For hard real-time work, this is worth measuring.

Programmer's Model & Register File

Sixteen 32-bit registers. Three special registers. A handful of rules from the AAPCS. That's the whole programmer's model — and once you internalize it, reading compiler output and writing inline assembly becomes natural.

The general-purpose register file

Cortex-M exposes sixteen 32-bit registers, named R0 through R15. The compiler treats some as freely usable and others as having special purposes. Knowing which is which is the difference between writing assembly that works and writing assembly that corrupts the stack.

Cortex-M register file
        ┌───────────────────────────────────────────────┐
        │  General-purpose, 32-bit each                 │
        ├───────────────────────────────────────────────┤
        │  R0 – R3     Caller-saved.  Arguments and       │
        │              return values. Scratch.          │
        │                                               │
        │  R4 – R11    Callee-saved.  Function must       │
        │              preserve these across calls.     │
        │                                               │
        │  R12 (IP)    Intra-procedure scratch.            │
        │              Used by linker for veneers.      │
        │                                               │
        │  R13 (SP)    Stack pointer. Banked: MSP / PSP    │
        │                                               │
        │  R14 (LR)    Link register. Holds return addr.   │
        │                                               │
        │  R15 (PC)    Program counter. Always +4 ahead    │
        │              of the executing instruction.    │
        └───────────────────────────────────────────────┘

        Special registers (accessed via MRS / MSR):
        ┌───────────────────────────────────────────────┐
        │  xPSR      Program status (APSR + IPSR + EPSR) │
        │  PRIMASK   Global interrupt enable bit         │
        │  FAULTMASK Disables all but NMI                │
        │  BASEPRI   Mask interrupts below this priority │
        │  CONTROL   Thread mode, stack select, FPU      │
        └───────────────────────────────────────────────┘

R13 — the banked stack pointer

R13 is not a single register. It is two registers — MSP (main stack pointer) and PSP (process stack pointer) — that share the R13 name. Which one R13 actually refers to depends on the processor mode:

  • Handler mode (inside an interrupt or exception) always uses MSP.
  • Thread mode (normal code) uses MSP by default, but can switch to PSP by writing the CONTROL register.

This dual-stack design is the foundation of RTOS task switching. Each task gets its own PSP-based stack; the kernel and interrupt handlers run on MSP. When a context switch happens, only the PSP changes — MSP stays fixed.

The AAPCS calling convention

The ARM Architecture Procedure Call Standard governs how functions pass arguments, return values, and preserve registers across calls. Every C compiler for Cortex-M follows it. Inline assembly must follow it too.

RegisterRolePreserved by
R0Argument 1, return valueCaller
R1Argument 2, second return wordCaller
R2 – R3Arguments 3 and 4Caller
R4 – R11Local variablesCallee — must save and restore
R12 (IP)Linker scratchCaller
R13 (SP)Stack pointerCallee — must be 8-byte aligned at calls
R14 (LR)Return addressCaller — but callee saves it if it makes calls

Arguments 5 and beyond are passed on the stack, in order, with the first stacked argument at the lowest address. Return values larger than 64 bits are returned via a hidden pointer argument in R0.

Note — 8-byte stack alignment

The stack must be 8-byte aligned at every public function call boundary. Cortex-M can run with 4-byte alignment internally but exception entry hardware aligns to 8 bytes by default. If your inline assembly pushes an odd number of words, the next call may misalign and crash on FPU instructions or doubles.

Reading a real function in disassembly

Consider this trivial C function:

Cadd_three.c
int add_three(int a, int b, int c) {
    return a + b + c;
}

Compiled with arm-none-eabi-gcc -O2 -mthumb -mcpu=cortex-m4, the disassembly is:

ASMadd_three.s
add_three:
    add     r0, r0, r1   @ r0 = a + b
    add     r0, r0, r2   @ r0 = (a+b) + c
    bx      lr           @ branch to address in LR -- the return

Three observations:

  • Arguments came in via R0, R1, R2 — that's AAPCS in action.
  • The return value sits in R0 — AAPCS again.
  • No stack frame was needed because the function uses only argument registers, makes no calls, and has no locals. This is called a leaf function.

The xPSR — three status registers in one

The Program Status Register is actually three logical registers packed into one 32-bit value, named APSR, IPSR, and EPSR. They overlap on the same bits and you usually read them as the combined xPSR.

xPSR layout
  31  30  29  28  27 ─── 24  23 ─── 10  9    8 ─── 0
  ┌───┬───┬───┬───┬─────────┬─────────┬───┬─────────┐
  │ N │ Z │ C │ V │   ...   │   ICI   │ T │ ISR_NUM │
  └───┴───┴───┴───┴─────────┴─────────┴───┴─────────┘
   │   │   │   │              │        │       │
   │   │   │   └ Overflow     │        │       └ Current exception
   │   │   └ Carry            │        │         (0 = thread mode)
   │   └ Zero                 │        │
   └ Negative                 │        └ Thumb state -- must be 1
                              │
                              └ Interrupt-continuable instruction
                                bits, used during LDM/STM resume

Three groups of bits, three names:

  • APSR (Application PSR) — the four condition flags N, Z, C, V set by ALU operations.
  • IPSR (Interrupt PSR) — the bottom 9 bits identify the currently executing exception. Zero means thread mode.
  • EPSR (Execution PSR) — the Thumb-state bit (always 1 on Cortex-M) and the ICI/IT bits used during interruptible instructions.

Reading the special registers in C

You cannot access PRIMASK, BASEPRI, or CONTROL with normal C — they aren't memory-mapped. You need the MRS and MSR instructions, which CMSIS wraps in intrinsics:

Cspecial_regs.c
#include "cmsis_compiler.h"

/* Globally disable interrupts. Equivalent to "cli" on x86. */
void enter_critical(void) {
    __disable_irq();  /* sets PRIMASK = 1 */
}

/* Disable interrupts whose priority is >= 4 (i.e. less urgent). */
/* Higher-priority interrupts still fire.                         */
void enter_partial_critical(void) {
    __set_BASEPRI(4 << (8 - __NVIC_PRIO_BITS));
}

/* Detect whether we are currently inside an ISR. */
int in_interrupt(void) {
    return (__get_IPSR() != 0);
}

/* Switch the current task to use PSP (typical RTOS startup). */
void switch_to_psp(uint32_t stack_top) {
    __set_PSP(stack_top);
    __set_CONTROL(0x02);  /* SPSEL = 1, use PSP in thread mode */
    __ISB();                /* instruction barrier -- mandatory */
}
Gotcha — the ISB after CONTROL change

Writing to CONTROL takes effect immediately, but the pipeline may already have fetched instructions that assume the old stack pointer. The __ISB() instruction synchronization barrier flushes the pipeline so subsequent instructions see the new state. Without it, behaviour is undefined.

The exception-stacked frame

When any exception (interrupt, fault, SVC) fires on Cortex-M, the hardware automatically pushes eight registers onto the current stack before vectoring to the handler. This is how the handler gets its own R0–R3 to work with while preserving the interrupted task's state.

Stack frame pushed by exception entry
                  ┌─────────────────┐  ← SP before exception
   xPSR  ──────▶  │     xPSR        │
   PC    ──────▶  │     PC          │
   LR    ──────▶  │     LR          │
   R12   ──────▶  │     R12         │
   R3    ──────▶  │     R3          │
   R2    ──────▶  │     R2          │
   R1    ──────▶  │     R1          │
   R0    ──────▶  │     R0          │  ← SP at start of handler
                  └─────────────────┘
                       ↑ grows down

   Hardware pushes 8 x 32-bit = 32 bytes.
   With FPU + lazy stacking, 17 more words may be reserved.

This means you can write an exception handler in pure C — the compiler will save R4–R11 itself if it needs them, and the hardware already saved R0–R3 and the return state. You do not need a wrapper assembly trampoline for ordinary ISRs.

Interview Questions

Interview Question

What is the AAPCS, and why should an embedded developer care about it?

Answer

The ARM Architecture Procedure Call Standard defines how functions pass arguments, return values, and preserve registers across calls on ARM. It is the contract the C compiler follows when emitting function entry and exit code.

You care because:

  • Inline assembly must follow AAPCS if it calls C functions or is called from C. Clobbering R4–R11 without saving them corrupts the caller's state.
  • Reading disassembly requires it — you need to know that R0 holds the first argument and the return value to make sense of compiled code.
  • Reasoning about stack usage and ISR latency depends on knowing what the compiler will save (R4–R11) versus what the hardware saves automatically (R0–R3, R12, LR, PC, xPSR).
  • Linking C++ with C and vice versa requires understanding which registers may pass hidden arguments like the this pointer (passed in R0 for member functions).
Interview Question

Why does Cortex-M have two stack pointers, MSP and PSP? When are they used?

Answer

The dual stack pointer design lets you cleanly separate kernel and interrupt code (running on MSP) from user task code (running on PSP). This is essential for an RTOS.

The mechanics:

  • After reset, the CPU uses MSP for everything. The Reset_Handler runs on MSP. main() runs on MSP.
  • When an exception fires, the CPU always uses MSP in handler mode, regardless of what thread mode was using.
  • An RTOS will, during the first task switch, write the CONTROL register to make thread mode use PSP. Each task gets its own PSP-based stack.
  • From then on: task code runs on PSP, kernel and ISRs run on MSP. A context switch only changes PSP — MSP stays fixed.

Benefits: task stack overflow can't corrupt the kernel's stack. Interrupts always have a known, fixed stack to land on. You can configure MPU regions separately for kernel and task code.

Interview Question

When an interrupt fires on Cortex-M, which registers are automatically saved by hardware, and which must the handler save?

Answer

Hardware automatically pushes eight 32-bit words onto the current stack on exception entry: R0, R1, R2, R3, R12, LR, PC, and xPSR. This is called the exception stack frame.

If the FPU is active and lazy stacking is configured, the hardware also reserves space for S0–S15 and FPSCR but defers the actual save until the handler touches the FPU.

The handler must save R4–R11 itself if it uses them. But because handlers are typically written in C, the compiler emits push/pop for these as part of the prologue/epilogue. You almost never need to think about it.

This automatic stacking is also why Cortex-M interrupt entry is so fast — about 12 cycles on M3/M4 — and why you can write ISRs in pure C with no assembly wrapper.

Interview Question

What is the difference between PRIMASK, FAULTMASK, and BASEPRI?

Answer

All three control interrupt masking, but with different granularity:

  • PRIMASK — a single bit. When set to 1, all configurable interrupts and exceptions are masked. NMI and HardFault still fire. This is what __disable_irq() sets. Think "cli" on x86.
  • FAULTMASK — like PRIMASK but more aggressive. Also masks HardFault. Only NMI can fire. Used by fault handlers to prevent nested faults.
  • BASEPRI — an 8-bit priority threshold. Interrupts with priority numerically greater than or equal to BASEPRI are masked; higher-priority (numerically lower) interrupts still fire. This is the right primitive for an RTOS that wants to protect critical sections without disabling its most urgent interrupts.

An RTOS like FreeRTOS uses BASEPRI in its critical sections so that timing-critical ISRs (configMAX_SYSCALL_INTERRUPT_PRIORITY and above) keep running even while the scheduler is locked. The kernel doesn't touch PRIMASK in normal operation.

Interview Question

Given the C function int sum(int *arr, int n) that sums an array, sketch the AAPCS register usage at the entry and explain what R0 holds during the loop.

Answer

At entry, AAPCS dictates:

  • R0 = arr (the pointer)
  • R1 = n (the count)
  • LR = return address

During the loop, the compiler typically does this:

  • R0 may be repurposed to hold the running accumulator, because R0 is also the return register and starting the accumulation in R0 saves a move at the end.
  • R1 may hold the remaining count, decremented each iteration.
  • R2 or R3 holds the current pointer (a copy of the original R0).

You can verify this by compiling with -O2 -mthumb -mcpu=cortex-m4 and looking at the disassembly. The key insight for an interviewer is: R0 enters as the first argument, may be reused for any purpose during the function (since it's caller-saved), and must hold the return value at the BX LR.

Memory Map, Bus Matrix & AHB / APB

Every Cortex-M sees the world through a fixed 4 GB address map. The genius is that vendors carve out their flash, SRAM, and peripherals within an architectural framework that's identical across silicon — making CMSIS and most driver patterns portable.

The four-gigabyte address space

Cortex-M provides a 32-bit linear address space — exactly 4 GB. ARM divides this into eight 512 MB regions, each with predefined access rules and intended use. The vendor's silicon places real memory into those regions; you, the firmware engineer, never see "all 4 GB" but you must know where in the map each thing lives.

Cortex-M architectural memory map
   0xFFFFFFFF ┌─────────────────────────────────┐
              │ Vendor-specific                 │ 0xE0100000 – 0xFFFFFFFF
              │ (often unused on small MCUs)    │
   0xE0100000 ├─────────────────────────────────┤
              │ Private Peripheral Bus (PPB)    │ NVIC, SysTick, MPU,
              │                                 │ SCB, ITM, DWT, ETM
   0xE0000000 ├─────────────────────────────────┤
              │ External device                 │ Generally unused on small MCUs
   0xA0000000 ├─────────────────────────────────┤
              │ External RAM                    │ SDRAM, QSPI memory-mapped
   0x60000000 ├─────────────────────────────────┤
              │ Peripheral                      │ UART, SPI, I2C, GPIO
              │ (with bit-band alias 0x42xxxxxx)│ Timer, DMA, ADC ...
   0x40000000 ├─────────────────────────────────┤
              │ SRAM                            │ On-chip RAM lives here
              │ (with bit-band alias 0x22xxxxxx)│
   0x20000000 ├─────────────────────────────────┤
              │ CODE                            │ Flash, possibly aliased ROM
              │ (where vector table lives)      │
   0x00000000 └─────────────────────────────────┘

This layout is part of the ARM architecture, not a vendor decision. Every Cortex-M chip — STM32, nRF52, LPC, EFM32, MAX32 — places its NVIC and SysTick at exactly the same addresses. That is why a single CMSIS header works across all vendors.

What lives where

RangeRegionWhat's there
0x00000000 – 0x1FFFFFFFCODEInternal flash; vector table at 0x00000000 after reset. May be aliased to flash's true address.
0x20000000 – 0x3FFFFFFFSRAMOn-chip SRAM. Vendor places the actual bytes anywhere in this region.

Key Idea — the PPB at 0xE0000000

Everything the Cortex-M core itself provides — interrupt controller, system timer, fault handlers, debug, trace — lives in the PPB region. This region is not accessible to DMA controllers and bypasses the bus matrix. Reads and writes here go directly to the core's internal logic.

The bus matrix

Inside the chip, the Cortex-M core does not directly talk to flash, SRAM, and peripherals. Instead, those memories sit behind a bus matrix — a crossbar switch that arbitrates between the core's I-bus, D-bus, and S-bus on one side, and the various memory and peripheral interfaces on the other.

The bus matrix is why DMA can run concurrently with the CPU — they have separate ports into the matrix and can access different slaves in parallel. If CPU is reading flash and DMA is writing SRAM, both proceed at full speed. If both want the same slave, the matrix arbitrates and one waits.

AHB vs APB — high speed and low speed

ARM defined two bus protocols, both part of the AMBA (Advanced Microcontroller Bus Architecture) family:

  • AHB — Advanced High-performance Bus. Pipelined, supports burst transfers, runs at the system clock (often 100+ MHz). Used for flash, SRAM, DMA, and high-bandwidth peripherals like Ethernet and USB.
  • APB — Advanced Peripheral Bus. Simpler, lower-speed, two-cycle minimum per transfer, runs at a divided clock (often 50 MHz or less). Used for slow peripherals — UART, SPI, I2C, GPIO, timers.

A typical chip will have multiple bus instances:

Gotcha — APB timer clock multiplier

On STM32 chips, when an APB prescaler is greater than 1, the timer clock on that bus is automatically doubled. So if APB1 runs at HCLK/4, the timers on APB1 still run at HCLK/2. This catches everyone the first time. Always read the clock tree diagram carefully.

Reading peripheral registers — the volatile rule

Peripheral registers live in the Peripheral region (0x40000000+). They are memory-mapped — you read and write them like any byte in RAM. But you must mark them volatile so the compiler does not optimize away accesses.

Cperipheral_access.c
#include <stdint.h>

/* Manually defining a GPIO register block on STM32F4 */
typedef struct {
    volatile uint32_t MODER;     /* Mode register     */
    volatile uint32_t OTYPER;    /* Output type       */
    volatile uint32_t OSPEEDR;   /* Speed             */
    volatile uint32_t PUPDR;     /* Pull-up/down      */
    volatile uint32_t IDR;       /* Input data        */
    volatile uint32_t ODR;       /* Output data       */
    volatile uint32_t BSRR;      /* Bit set/reset     */
    volatile uint32_t LCKR;      /* Lock register     */
    volatile uint32_t AFR[2];    /* Alt function low/high */
} GPIO_TypeDef;

/* Place a struct at the GPIOA base address                     */
/* On STM32F4, AHB1 starts at 0x40020000, GPIOA at offset 0     */
#define GPIOA  ((GPIO_TypeDef *)0x40020000)

void gpio_set_pin13(void) {
    GPIOA->BSRR = (1 << 13);      /* atomic set bit 13   */
}

void gpio_clr_pin13(void) {
    GPIOA->BSRR = (1 << (13+16)); /* atomic clear bit 13 */
}

Without volatile on each register, the compiler is free to cache reads and drop "redundant" writes — and your firmware breaks in subtle, optimization-level-dependent ways.

Bit-banding — atomic single-bit access

Cortex-M3 and M4 (but not M0, M0+, M7, M33) implement bit-banding: a 1 MB region of SRAM (0x20000000 – 0x200FFFFF) and a 1 MB region of peripherals (0x40000000 – 0x400FFFFF) are aliased into 32 MB regions where each bit gets its own word address.

Bit-banding alias
   Original SRAM region (1 MB):
   0x20000000  ┌──── byte 0 ───── byte 1 ───── byte 2 ───
               │ bbbbbbbb       bbbbbbbb        ...
               └─...

   Bit-band alias (32 MB):
   0x22000000  ┌── word for bit 0 of byte 0
   0x22000004  ├── word for bit 1 of byte 0
   0x22000008  ├── word for bit 2 of byte 0
        ...
   0x2200001C  ├── word for bit 7 of byte 0
   0x22000020  ├── word for bit 0 of byte 1
        ...

   Writing 1 to alias address sets that bit atomically.
   Writing 0 clears it atomically.
   Reading returns 0 or 1.

The address calculation: alias = 0x22000000 + (byte_offset * 32) + (bit_number * 4).

Cbitband.c
/* Atomic single-bit access via bit-banding (M3/M4 only)        */
#define BITBAND_SRAM(addr, bit) \
    ((volatile uint32_t *)(0x22000000 + \
        (((uint32_t)(addr) - 0x20000000) << 5) + \
        ((bit) << 2)))

uint32_t shared_flags;

/* These are guaranteed atomic on M3/M4 even without disabling IRQs */
void set_flag_3(void)   { *BITBAND_SRAM(&shared_flags, 3) = 1; }
void clear_flag_3(void) { *BITBAND_SRAM(&shared_flags, 3) = 0; }
int  test_flag_3(void)  { return *BITBAND_SRAM(&shared_flags, 3); }

Bit-banding was the Cortex-M3/M4 era's solution to read-modify-write hazards. On M7 and later, ARM removed it because exclusive load/store instructions (LDREX/STREX) provide more general atomicity. Modern code typically uses CMSIS atomic intrinsics or C11 <stdatomic.h>.

Interview Questions

Interview Question

Why is the Cortex-M memory map "fixed" by ARM, and what flexibility do silicon vendors retain?

Answer

ARM defines the eight 512 MB regions and their access attributes. The architectural reasons:

  • Portability of system software. CMSIS, RTOS kernels, debug tools all assume NVIC lives at 0xE000E100, SysTick at 0xE000E010, etc. If each vendor moved them, every piece of software would be vendor-specific.
  • Speculative execution and prefetching rules. The architecture defines which regions are "device" (no speculation, no reordering) versus "normal" (cacheable, reorderable). Flash is Normal; the PPB is Strongly Ordered. The CPU's memory system relies on these region attributes.
  • MPU defaults. Even without MPU configuration, the default region attributes provide reasonable behavior.

Vendors choose:

  • Whether to populate each region, and how much memory to expose.
  • What peripherals to map into the Peripheral region and at what offsets.
  • Whether to provide flash aliases (e.g., STM32 maps flash at 0x00000000 and 0x08000000).
  • How to populate the External RAM region — many small MCUs leave it empty.
Interview Question

What is the difference between AHB and APB? Why don't vendors use AHB everywhere?

Answer

AHB is the high-performance bus — pipelined, supports burst transfers, can run at the full system clock. APB is the peripheral bus — simpler, two-cycle minimum per transfer, runs at a divided clock.

Vendors don't put everything on AHB because:

  • Silicon area and power. AHB peripherals need more logic — burst state machines, pipeline registers. For a UART that runs at 1 Mbps, that's wasteful. APB's simple two-phase access is plenty.
  • Clocking. A simple peripheral can tolerate a slower clock, saving dynamic power. Running an I2C controller at 168 MHz when the bus operates at 400 kHz is pointless.
  • Bus crowding. Putting everything on one bus would create contention. Splitting peripherals across AHB and APB (and across multiple APB instances) lets DMA and CPU access different peripherals simultaneously.

Typical division: anything bandwidth-critical (DMA, USB, Ethernet, external memory) goes on AHB. Everything else (UART, SPI, I2C, GPIO, timers, ADC) goes on APB.

Interview Question

What is bit-banding and what problem does it solve?

Answer

Bit-banding is a Cortex-M3 and M4 feature that aliases each bit in a 1 MB SRAM region (and a 1 MB peripheral region) to its own 32-bit address. Writing 1 to the alias address sets that bit atomically; writing 0 clears it.

It solves the read-modify-write hazard that exists when toggling a single bit in a shared variable. Without bit-banding:

shared |= (1 << 3);   // load shared, OR, store back
                      // interrupt in the middle breaks atomicity

With bit-banding, the alias write is a single bus transaction that atomically modifies just bit 3 of the underlying word. No interrupt can interleave.

ARM removed bit-banding from M7 and later cores because exclusive load/store instructions (LDREX/STREX) and proper atomic primitives provide more general solutions. Modern code uses <stdatomic.h> or CMSIS atomic intrinsics.

Interview Question

Why must peripheral registers be declared volatile?

Answer

The C compiler assumes that ordinary memory has no side effects beyond reads and writes. Under that assumption, it freely optimizes:

  • If you write the same value twice, the second write may be dropped.
  • If you read a location without modifying it in between, the second read may be replaced by the cached value.
  • Read and write orders may be reordered if dependencies allow.

Peripheral registers break all three assumptions. Reading a UART data register has the side effect of consuming a byte from the FIFO. Writing to a control register triggers hardware action. Writing twice may be necessary because the hardware latches on each edge.

volatile tells the compiler: this location may change without my code touching it, and every read and write I write must produce a real bus transaction in the order I wrote them.

Note that volatile is not sufficient for thread safety across CPU cores or for ordering with DMA — for those you need memory barriers (__DMB, __DSB) or atomic primitives.

Pipeline, Branch Prediction & Counters

Modern Cortex-M cores look like simple in-order machines on the outside, but underneath they pipeline instructions, predict branches, and provide cycle-accurate counters that let you measure exactly how long anything takes. Mastering these turns a black-box CPU into an instrument.

The Cortex-M pipeline

Cortex-M is an in-order machine — instructions retire in the order they were fetched — but it pipelines fetch, decode, and execute so that multiple instructions are in flight simultaneously. The pipeline depth varies by core:

CoreStagesDispatchBranch prediction
Cortex-M0 / M0+3 (Fetch, Decode, Execute)Single-issueNone — branches always flush
Cortex-M3 / M43 (Fetch, Decode, Execute)Single-issueSimple — predicts branches as taken
Cortex-M76 (Fetch1, Fetch2, Decode, Issue, Execute, Writeback)Dual-issue (superscalar)Branch predictor unit (BPU)
Cortex-M333 (Fetch, Decode, Execute)Single-issueOptional BPU
Cortex-M3/M4 three-stage pipeline
   Time  ─────────────────────────────────────────────▶

   Cycle 1     Cycle 2     Cycle 3     Cycle 4     Cycle 5

   ┌──────┐
   │ ADD  │ Fetch    Decode    Execute
   └──────┘
            ┌──────┐
            │ SUB  │  Fetch    Decode    Execute
            └──────┘
                     ┌──────┐
                     │ LDR  │  Fetch    Decode    Execute
                     └──────┘
                              ┌──────┐
                              │ STR  │  Fetch    Decode    Execute
                              └──────┘

   At any cycle, three instructions are in flight in different stages.
   Throughput approaches one instruction per cycle in straight-line code.

Why R15 (PC) always reads ahead by 4

Because the pipeline fetches ahead, when an instruction reads the PC, it gets the address of the next next instruction — not the currently executing one. On Cortex-M (Thumb-2), this means PC reads as current_instruction_address + 4.

This is invisible most of the time but it matters for hand-written assembly that uses PC-relative addressing, and for instructions like BLX PC which would target an address 4 bytes ahead.

Branch handling

When a branch is taken, the instructions already in the pipeline behind it are wrong — they were the sequential continuation. The pipeline must flush them and refill from the branch target. This is called a branch penalty, and it costs cycles:

  • Cortex-M0: 3-cycle penalty (entire pipeline flush).
  • Cortex-M3/M4: 1-3 cycle penalty depending on alignment and whether the target is in the prefetch buffer.
  • Cortex-M7: Branch predictor speculates ahead; correct prediction is free, misprediction costs ~5 cycles.
Note — branch density matters

Tight loops with one branch back to the top run nearly at peak throughput because the predictor learns the pattern. Code dense with unpredictable branches (state machines, switch statements with cold paths) pays the misprediction tax repeatedly. This is why DSP code unrolls loops and avoids data-dependent branches.

DWT and the cycle counter

The Data Watchpoint and Trace (DWT) unit lives in the PPB at 0xE0001000. It provides a free-running 32-bit cycle counter (DWT->CYCCNT) that ticks once per CPU clock. This is the single most useful debugging tool you have for measuring execution time.

Ccycle_counter.c
#include "core_cm4.h"

/* One-time setup at boot */
void dwt_init(void) {
    /* Enable the DWT and ITM block in DEMCR */
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;

    /* Reset and enable the cycle counter */
    DWT->CYCCNT = 0;
    DWT->CTRL   |= DWT_CTRL_CYCCNTENA_Msk;
}

/* Measure the cycle cost of a code region */
uint32_t measure_cycles(void (*fn)(void)) {
    uint32_t start = DWT->CYCCNT;
    fn();
    uint32_t end   = DWT->CYCCNT;
    return end - start;  /* unsigned subtraction handles wraparound */
}

/* Microsecond-resolution delay using the cycle counter */
void delay_us(uint32_t us) {
    extern uint32_t SystemCoreClock;
    uint32_t cycles = us * (SystemCoreClock / 1000000);
    uint32_t start  = DWT->CYCCNT;
    while ((DWT->CYCCNT - start) < cycles) {}
}

Using CYCCNT to benchmark

Cbenchmark_example.c
/* Compare two implementations of the same hash function */
uint32_t hash_naive(const uint8_t *data, size_t len);
uint32_t hash_unrolled(const uint8_t *data, size_t len);

void compare_implementations(void) {
    uint8_t buf[256];
    uint32_t sink;  /* prevent the compiler from eliding the call */

    uint32_t t1 = DWT->CYCCNT;
    sink = hash_naive(buf, sizeof(buf));
    uint32_t t2 = DWT->CYCCNT;

    uint32_t t3 = DWT->CYCCNT;
    sink = hash_unrolled(buf, sizeof(buf));
    uint32_t t4 = DWT->CYCCNT;

    printf("naive:    %u cycles\n", (unsigned)(t2 - t1));
    printf("unrolled: %u cycles\n", (unsigned)(t4 - t3));
    (void)sink;
}

These counters are 8-bit each and overflow quickly, so you sample them on every iteration of a benchmark. They are invaluable for finding the actual bottleneck — is the inner loop waiting on memory? Spending time in interrupt overhead? You can see it directly.

Interview Questions

Interview Question

How does pipelining affect interrupt latency on Cortex-M?

Answer

Pipelining means multiple instructions are partially executed at any moment. When an interrupt fires, the core must reach a clean boundary before vectoring to the handler — finishing or abandoning in-flight instructions, pushing the exception frame, fetching the vector, and starting the handler.

On Cortex-M3 and M4 the published worst-case latency is 12 cycles from interrupt assertion to first handler instruction. This breaks down roughly as:

  • Detecting the interrupt and arbitrating priority (~2 cycles)
  • Finishing the current instruction or aborting if interruptible (load/store multiple)
  • Stacking R0-R3, R12, LR, PC, xPSR (8 words, 8 cycles)
  • Fetching the vector table entry (~1 cycle, can be pipelined with stacking)
  • Starting the handler

On Cortex-M7 with its deeper pipeline and branch predictor, typical latency is similar but worst-case can be longer because of branch misprediction in critical pre-interrupt instructions. For hard-real-time work, always measure with DWT and design for worst case.

Interview Question

Cortex-M0 has no branch predictor — how does it handle branches?

Answer

Cortex-M0 simply flushes the pipeline on every taken branch. The 3-stage pipeline means two instructions behind the branch were already fetched and decoded but must be discarded.

The penalty is approximately 3 cycles per taken branch. Untaken branches (fallthrough) have no penalty — the pipeline keeps fetching sequentially.

This is why M0 code is more sensitive to branch density than M4. Tight unrolled loops without internal branches run very close to peak throughput; code with many if/else chains runs much slower. DSP libraries for M0 are deliberately structured to minimize branches, often using conditional MOV or arithmetic tricks instead of explicit branches where possible.

Interview Question

You measure a function with DWT->CYCCNT and get wildly inconsistent results between runs. What could be going on?

Answer

Several common sources of variance:

  • Interrupts firing during the measurement. SysTick alone adds dozens of cycles. Disable interrupts (or at least mask irrelevant ones) for the measured region.
  • Flash wait states and cache behavior. First execution after reset hits cold flash and the ART/cache. Subsequent runs are faster. Always run a warm-up iteration before measuring.
  • Branch prediction state. On M7, the first run through new code mispredicts; subsequent runs are faster.
  • DMA traffic on the bus matrix. If DMA is moving data while you're executing, bus contention adds cycles.
  • Different code alignment between builds. The compiler may place the function at a different alignment, affecting prefetch behavior.
  • Compiler optimization eliding the work. If your benchmark's result isn't used, the compiler may discard the whole computation. Always sink the result to a volatile or pass it out.

Best practice: disable interrupts, run a warm-up, take the minimum of N runs, and verify against the disassembly that the work you're measuring is actually emitted.

Interview Question

Why does the PC register on Cortex-M read as the current instruction address plus 4?

Answer

Because of the three-stage pipeline. While an instruction is in the Execute stage, the Fetch stage has already retrieved the instruction two slots ahead. The PC visible to the executing instruction therefore points to the instruction being fetched, not to the one executing.

For Thumb-2 code where most instructions are 2 bytes, "two slots ahead" is 4 bytes. So PC = current_instruction_address + 4.

This is mostly invisible — instructions like LDR Rn, [PC, #offset] work correctly because the assembler and compiler account for the +4 offset automatically. But if you hand-write assembly that does arithmetic on PC, or you're reading a faulted PC from the stacked exception frame to find where a fault occurred, you need to subtract the offset.

For exception analysis specifically: the stacked PC points to the instruction that would have executed next, not the one that faulted. To find the faulting instruction, you typically subtract 2 or 4 bytes (depending on the instruction encoding length) — or use the BFAR/MMFAR fault address registers when available.

Cache Hierarchy, MMU & TLB

Caches turn slow external memory into something almost as fast as the CPU. The MMU translates virtual addresses to physical ones, enabling protected processes and virtual memory. Both are essential to Cortex-A, optional on Cortex-M7, and absent on smaller M cores — which is why understanding them changes how you write portable firmware.

Why caches exist

CPU clocks have risen by orders of magnitude over four decades. DRAM access times have barely changed. The gap is enormous: a modern Cortex-A can execute hundreds of instructions in the time it takes to read one byte from DDR. Caches close that gap by keeping recently-used data and instructions in small, very fast on-chip memory.

Memory hierarchy on a typical Cortex-A SoC
   Register file       0 cycle      ~100 bytes
       │
       ▼
   L1 I-cache          1-3 cycles   16-64 KB
   L1 D-cache          1-3 cycles   16-64 KB
       │
       ▼
   L2 cache (unified)  ~10 cycles   256 KB - 2 MB
       │
       ▼
   External DDR        ~100 cycles  Gigabytes
       │
       ▼
   eMMC / SD card      thousands    Tens of GB

   Each level is roughly 10x slower and 10x larger than the one above.

On Cortex-M7, you typically have L1 caches only — there is no L2 in most M-class chips. On Cortex-A, you have L1 plus L2, and on multi-core designs an L3 shared between cores.

Cache organization

A cache is divided into cache lines, typically 32 or 64 bytes each. When the CPU accesses any byte, the cache reads or writes the entire line containing it. This is why spatial locality matters — accessing data sequentially is much faster than scattered access.

Caches are organized by associativity:

  • Direct-mapped: each address has exactly one slot in the cache. Simple but suffers from conflicts.
  • N-way set associative: each address can live in any of N slots. Cortex-M7 D-cache is typically 4-way; Cortex-A is often 8-way.
  • Fully associative: any address can live anywhere. Used only for small structures like TLBs.
Cache line lookup (4-way set associative)
   32-bit address:  [ Tag : 20 bits ][ Set : 7 bits ][ Offset : 5 bits ]

   - Offset selects byte within the 32-byte line
   - Set indexes which of 128 sets to check
   - Tag is compared against all 4 ways in that set

       Set 0   ┌──── way 0 ────┬──── way 1 ────┬──── way 2 ────┬──── way 3 ────┐
               │ V  D  Tag  Data│ V  D  Tag  Data│ V  D  Tag  Data│ V  D  Tag  Data│
       Set 1   ├────────────────┼────────────────┼────────────────┼────────────────┤
        ...    │                │                │                │                │
       Set 127 ├────────────────┼────────────────┼────────────────┼────────────────┤
               └────────────────┴────────────────┴────────────────┴────────────────┘

   V = Valid bit, D = Dirty bit (modified vs main memory)
   On hit: data returned in 1-3 cycles.
   On miss: line evicted (write-back if dirty), new line fetched.

Write-back vs write-through

When the CPU writes to a cached line, the cache has two choices:

  • Write-through: every write propagates immediately to main memory. Simple, but slow — every write incurs the full memory latency. Used for memory-mapped peripherals and sometimes for safety-critical caches.
  • Write-back: writes hit the cache only. The line is marked dirty. When evicted, the entire dirty line is written back to memory. Much faster but creates coherency problems with DMA.
Gotcha — DMA and write-back cache

If the CPU writes to a buffer that DMA will transmit, the data lives in the dirty cache line. Until the line is flushed, DMA reads stale data from main memory. Always SCB_CleanDCache_by_Addr() before starting a DMA-out transfer, and SCB_InvalidateDCache_by_Addr() after a DMA-in transfer. This is the most common bug in Cortex-M7 firmware.

Cdma_cache_safe.c
#include "core_cm7.h"

/* DMA buffer must be 32-byte aligned (cache line size on M7)    */
/* and its size must be a multiple of 32, otherwise neighbours    */
/* in the same line get corrupted by clean/invalidate.            */
__attribute__((aligned(32)))
uint8_t tx_buffer[256];

void dma_start_tx(size_t len) {
    /* Make sure CPU's cached writes hit main memory               */
    SCB_CleanDCache_by_Addr((uint32_t *)tx_buffer, len);

    /* Now safe to tell DMA to read from tx_buffer                 */
    DMA_Stream->PAR = (uint32_t)&USART->DR;
    DMA_Stream->M0AR = (uint32_t)tx_buffer;
    DMA_Stream->NDTR = len;
    DMA_Stream->CR  |= DMA_SxCR_EN;
}

__attribute__((aligned(32)))
uint8_t rx_buffer[256];

void dma_complete_rx(size_t len) {
    /* Discard cached copies so next read sees fresh DMA data      */
    SCB_InvalidateDCache_by_Addr((uint32_t *)rx_buffer, len);

    process_buffer(rx_buffer, len);
}

The MMU — virtual memory and protection

Where the MPU on Cortex-M enforces access rules on small numbers of regions, the MMU on Cortex-A provides full virtual memory: every memory access goes through a translation step that maps virtual addresses (what the program sees) to physical addresses (what the DRAM actually has).

MMU translation flow
   CPU issues virtual address: 0x76543210
        │
        ▼
   ┌─────────────────────────┐
   │      TLB lookup         │      Translation Lookaside Buffer
   │  (cached translations)  │      ─ small, very fast
   └─────────┬───────────────┘
             │
        hit  │  miss
             │     │
             ▼     ▼
       physical   ┌──────────────────────────┐
        address   │   Page table walk        │
             │   │  (read L1, L2, ... PTE   │
             │   │   from main memory)      │
             │   └────────────┬─────────────┘
             │                │
             ▼                ▼
       To cache /        TLB updated,
       memory subsystem  physical address used

The translation gives you three powerful capabilities:

  • Per-process address spaces. Each process sees the same virtual addresses (e.g., code at 0x00400000) but they map to different physical pages. Processes can't accidentally access each other's memory.
  • Memory protection. The page table entry contains permission bits (read, write, execute, user/kernel). Violations cause faults the kernel handles.
  • Demand paging and swapping. A page can be marked as not-present; access faults; kernel loads it from disk; resumes execution. This is how Linux supports more virtual memory than physical RAM.

The TLB — caching translations

Walking the page table on every memory access would be devastating. A page walk on ARMv8-A may take 5+ memory references just to translate one virtual address. The Translation Lookaside Buffer (TLB) is a small, fully-associative cache of recent translations.

A typical Cortex-A TLB has 32-256 entries. When the CPU issues a virtual address, the TLB checks all its entries in parallel. A hit gives the physical address in one cycle. A miss triggers a page walk and inserts the result into the TLB, possibly evicting an older entry.

Key Idea — context switches and TLB flushes

When the OS switches to a different process with a different page table, all TLB entries for the old process become invalid (their virtual-to-physical mappings no longer apply). Historically this required a full TLB flush on every context switch — expensive. Modern ARM cores tag TLB entries with an Address Space ID (ASID) so multiple processes' translations coexist in the TLB. Only the kernel-global pages need flushing, and most user-space translations survive context switches.

The MPU — protection without translation

Cortex-M doesn't have an MMU because microcontrollers don't run general-purpose OSes that need virtual memory. Instead, Cortex-M (M3 and up) provides an MPU — a Memory Protection Unit — that defines 8 or 16 regions in the physical address space and enforces access rules on each.

Cmpu_stack_guard.c
/* Cortex-M MPU: use one region as a stack-bottom guard for a task.   */
/* If the task's stack overflows into this region, a MemManage fault  */
/* fires immediately rather than corrupting unrelated memory.         */

void mpu_setup_stack_guard(uint32_t guard_addr) {
    /* Disable MPU while configuring */
    MPU->CTRL = 0;

    /* Select region 0 */
    MPU->RNR = 0;

    /* Base address must be aligned to region size           */
    /* 32 bytes = smallest MPU region                        */
    MPU->RBAR = guard_addr & ~0x1F;

    /* Size = 32 bytes (SIZE = 4), no access permitted        */
    MPU->RASR = (0 << 24)   /* AP = No access      */
              | (4 << 1)    /* SIZE = 32 bytes     */
              | MPU_RASR_ENABLE_Msk;

    /* Enable MPU with default background map for kernel */
    MPU->CTRL = MPU_CTRL_PRIVDEFENA_Msk
              | MPU_CTRL_ENABLE_Msk;

    __DSB(); __ISB();
}

What this means for Cortex-M firmware

Most Cortex-M firmware never thinks about cache because most M cores don't have one. But on M7-based chips like STM32H7 and i.MX RT, you must:

  • Mark DMA buffers as 32-byte aligned, multiples of 32 bytes long.
  • Clean the cache before DMA-out, invalidate before DMA-in.
  • Consider placing high-bandwidth buffers in tightly-coupled memory (TCM) which bypasses the cache.
  • Set up MPU regions for shared memory between cache and DMA to be non-cacheable if you can't manage clean/invalidate explicitly.

Interview Questions

Interview Question

What is the difference between write-back and write-through cache, and which does Cortex-M7 use by default?

Answer

Write-through propagates every CPU write to main memory immediately. Simple to reason about — main memory always reflects the latest write — but slow because every write incurs the full memory latency.

Write-back only updates the cache line and marks it dirty. The write to main memory is deferred until the line is evicted. Much faster — most writes never touch DRAM — but main memory becomes stale until eviction.

Cortex-M7's D-cache is configurable per MPU region. The default region type for SRAM is Normal, Cacheable, Write-Back, Write-Allocate. Peripheral regions are Device — never cached at all.

You should switch a region to write-through or non-cacheable when:

  • DMA reads from or writes to that region and you can't easily clean/invalidate.
  • You want predictable write latency (for real-time control).
  • Multi-core coherency is needed and the chip doesn't have a coherent interconnect.
Interview Question

Explain what an MPU is and how it differs from an MMU.

Answer

Both enforce memory access rules, but they're architecturally different.

An MMU translates virtual addresses to physical addresses using page tables stored in memory. Each process has its own page table, so processes can have private virtual address spaces that map to disjoint physical memory. The MMU also enforces permission bits (read/write/execute, user/kernel) per page. This is what makes modern operating systems possible.

An MPU does no translation. The CPU issues physical addresses directly. The MPU has a small number of programmable regions (typically 8 or 16) that define access rules — readable, writable, executable, privileged-only — for physical address ranges. When an access violates the rules, a fault fires.

MMU is for general-purpose computing with virtual memory and process isolation. MPU is for embedded systems where you want lightweight protection — preventing a task from corrupting another task's stack, marking flash as read-only at runtime, catching null pointer dereferences — without the cost and complexity of an MMU.

Interview Question

My DMA transfer on STM32H7 (Cortex-M7) sometimes sends garbage data. What is likely happening?

Answer

Classic cache coherency bug. On Cortex-M7 the D-cache is write-back by default. When the CPU prepares a buffer and tells DMA to send it:

  1. The CPU's writes update the L1 D-cache lines but mark them dirty — main memory is not yet updated.
  2. DMA reads from main memory and gets the stale contents — whatever was there before.
  3. Garbage gets transmitted.

The fix is to clean the D-cache for the buffer address range before starting the DMA:

SCB_CleanDCache_by_Addr((uint32_t *)tx_buffer, buffer_size);
HAL_UART_Transmit_DMA(&huart1, tx_buffer, buffer_size);

For DMA-in (peripheral to memory) the symptom is different — the CPU reads stale cached data instead of the freshly-DMA'd buffer. The fix is invalidate D-cache after the DMA completes, before reading:

SCB_InvalidateDCache_by_Addr((uint32_t *)rx_buffer, buffer_size);
process(rx_buffer);

Also critical: the buffer must be 32-byte aligned and a multiple of 32 bytes (the cache line size), or clean/invalidate operations will affect adjacent variables and corrupt them.

Interview Question

What is a TLB and why does its size matter?

Answer

The Translation Lookaside Buffer is a cache of recent virtual-to-physical address translations. Without it, every memory access would require walking the page tables — multiple dependent memory reads — which would be catastrophically slow.

The TLB is small (32 to a few hundred entries) and fully associative. A TLB hit returns the translation in 1 cycle. A TLB miss triggers a page walk that can take 10-50 cycles on a modern Cortex-A.

TLB size matters because each entry maps one page — typically 4 KB. With 64 TLB entries you can cover at most 256 KB of working set before missing. Programs with large working sets (databases, image processing) suffer TLB thrashing where translations keep getting evicted and re-walked.

ARM provides several mitigations: huge pages (2 MB or 1 GB instead of 4 KB) so one TLB entry covers more memory, ASID tagging so multiple processes share the TLB without flushing on context switch, and hardware prefetchers that anticipate page walks.

For embedded engineers working on Linux-based products (Cortex-A), TLB pressure is a real performance factor for memory-intensive workloads and can be improved by configuring the kernel to use huge pages for known hot regions.

Interview Question

Why is "spatial locality" important for cache performance?

Answer

Caches fetch entire cache lines (32 or 64 bytes), not individual bytes. When you access one byte, the cache loads the whole line containing it. Subsequent accesses to nearby bytes are cache hits and almost free.

Spatial locality is the property of accessing nearby addresses close together in time. Code with good spatial locality runs much faster than code that scatters access across memory:

  • Iterating a contiguous array hits every cache line once, then reuses it for 8-16 elements (assuming 32-byte line, 4-byte int). Near-perfect cache utilization.
  • Iterating a linked list randomly placed in memory misses on nearly every node — every traversal pays full memory latency. Often 10-100x slower than the array version.
  • Iterating a 2D array row by row in row-major C arrays: good locality. Column by column: terrible locality, because columns are non-contiguous in memory.

This is why "cache-friendly data structures" are a real engineering concern — even when the asymptotic complexity is the same, layout that respects spatial locality can make code run an order of magnitude faster.
