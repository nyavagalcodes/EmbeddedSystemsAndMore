Cache Hierarchy, MMU & TLB

When firmware runs faster on M7 than M4 by 5× instead of the expected 3×, that's the cache earning its keep. When DMA buffers corrupt themselves silently, that's the cache breaking your code.

Most Cortex-M cores don't have a cache. The M0, M0+, M3, M4, M23, and M33 all access memory directly — flash on the I-bus, SRAM on the S-bus, peripherals on the system bus. What you write goes where you wrote it, immediately. Predictable, deterministic, and easy to reason about.

Then the Cortex-M7 arrived with optional I-cache and D-cache, the M55 added it for vector loads, and the M85 brought a properly tuned cache hierarchy. Suddenly firmware that worked perfectly on Cortex-M4 was corrupting DMA buffers on Cortex-M7 in ways that depended on optimization level. This topic explains why — and how to write code that survives the transition.

It also covers the MMU and TLB, which exist on Cortex-A cores, but are absent from every M-profile core. Understanding the difference matters when you eventually move firmware from a microcontroller to a Linux-class system on a chip.

The cache — what it is, what it costs

A cache is a small, fast memory that sits between the CPU and main memory. When the CPU reads an address, the cache checks first; if the data is there (a hit), it's returned in 1–2 cycles. If not (a miss), the cache fetches the full cache line from main memory — typically 32 bytes — and stores it locally for next time.

Why caches break DMA

Imagine a typical DMA receive scenario. You allocate a buffer in SRAM, tell the DMA controller to write incoming UART bytes into it, and then read the buffer from your code. On a Cortex-M4 this works perfectly. On a Cortex-M7 with the cache enabled, your code reads stale data from the cache because:

  1. You read the buffer earlier, and the cache helpfully grabbed those (then-empty) bytes into a cache line.
  2. DMA wrote new data directly into SRAM, bypassing the cache.
  3. You read the buffer again — the cache hits and returns the old, empty bytes. The new data is sitting in SRAM, invisible.
Classic Bug

The symptom is unmistakeable: code that worked on STM32F4 (M4) silently corrupts on STM32H7 (M7). The data is in SRAM, you can see it in the debugger memory window, but your C code reads zeros. The fix is one of: place DMA buffers in DTCM (outside the cache), mark the buffer's memory region non-cacheable via MPU, or call SCB_InvalidateDCache_by_Addr() before reading.

Cache coherency — three approaches

There are three correct ways to handle DMA on a cached system:

Cdma_cache_safe.c
#include "core_cm7.h"     /* CMSIS for cache intrinsics */

/* APPROACH 1: place buffer in DTCM.
 * DTCM is single-cycle SRAM outside the cache.
 * Linker script must define a section pointing into DTCM. */
static uint8_t rx_buf[256] __attribute__((section(".dtcm_bss")));

/* APPROACH 2: mark the buffer region non-cacheable via MPU.
 * Set up an MPU region covering the buffer, attributes = Normal
 * non-cacheable. Costs an MPU slot but makes the buffer behave
 * like a non-cached chip without code changes. */

/* APPROACH 3: explicit cache maintenance around DMA. */
uint8_t dma_buf[256] __attribute__((aligned(32)));

void dma_receive(void)
{
    /* Before DMA writes our buffer, drop any cached lines.
     * DMA's writes go straight to SRAM; we want the CPU's
     * next read to come from SRAM, not from the cache. */
    SCB_InvalidateDCache_by_Addr((uint32_t *)dma_buf, sizeof(dma_buf));

    start_dma_into(dma_buf, sizeof(dma_buf));
    wait_for_dma_complete();

    /* Now we can safely read dma_buf — cache lines were
     * invalidated, so reads will fetch fresh data. */
}

void dma_transmit(const uint8_t *src, size_t n)
{
    /* Before DMA reads our data, flush the cache to SRAM.
     * Without this, DMA may read stale data because our
     * writes are sitting in the cache, not yet in SRAM. */
    SCB_CleanDCache_by_Addr((uint32_t *)src, n);

    start_dma_out(src, n);
}
Key Idea

Cache maintenance on Cortex-M7 has three operations: invalidate (mark cache lines as no-longer-valid, next read misses to memory), clean (write any dirty lines back to memory), and clean & invalidate (both together). For a DMA receive use invalidate before DMA. For a DMA transmit use clean before DMA. These are unambiguous rules — get them wrong and the bug will reproduce only sometimes, only with optimization, only on Tuesdays.

Cache organization — sets, ways, lines

Cortex-M7 caches are organized as set-associative: every memory address maps to one of several sets, and each set can hold a few cache lines (the "ways"). When a new line needs to come in, the cache picks a line in the same set to evict — usually the least recently used.

The implication: addresses that share the same index bits compete for the same set. If your hot loop reads from five different arrays whose addresses all happen to land in the same set, you'll thrash that set repeatedly — the cache effectively behaves as if it were a tiny 4-line buffer. This is called a conflict miss, and it's rare but spectacular when it bites.

Write policies — write-back versus write-through

When the CPU writes data to a cached address, the cache has two options:

  • Write-back — Update only the cache line, mark it "dirty", and write to main memory later (when the line is evicted). Fast, but the data isn't in main memory until eviction or an explicit clean.
  • Write-through — Update the cache and main memory simultaneously. Slower writes, but memory is always coherent.

Cortex-M7's D-cache supports both, configured per memory region via the MPU. Default is write-back for most regions. DMA-touched regions are commonly set to write-through or non-cacheable to avoid the coherency dance.

The MMU — present on Cortex-A, absent on Cortex-M

A Memory Management Unit translates virtual addresses (what software sees) into physical addresses (what the bus sees). It enables virtual memory, per-process address spaces, copy-on-write, memory-mapped files, and demand paging — all the features Linux relies on.

MMU translation pipeline (Cortex-A) ┌──────────┐ virtual addr ┌─────────┐ physical addr ┌──────────┐ │ CPU │ ─────────────────►│ MMU │ ───────────────►│ Bus │ └──────────┘ │ (+ TLB) │ └──────────┘ └─────────┘ │ ▼ Walks the page tables in DRAM if no TLB hit.

The MMU uses page tables stored in main memory. Each page table entry maps a virtual page (typically 4 KB) to a physical page, plus permission bits (readable, writable, executable, user/supervisor). When the CPU accesses a virtual address, the MMU walks the page table to find the translation — but page-table walks are slow, so most translations are cached in the TLB.

The TLB — fast translation cache

The Translation Lookaside Buffer is a small associative cache of recent virtual-to-physical translations. A TLB lookup is one cycle. A TLB miss costs a page-table walk — typically 5–20 cycles plus any cache misses along the walk.

This is why context switches in operating systems are expensive: switching processes usually means switching page tables, which invalidates the TLB, which means every memory access during the next several hundred instructions misses the TLB and pays the walk penalty.

Why M-profile has no MMU

The M-profile design philosophy is deterministic real-time response, low power, and small silicon. An MMU breaks all three:

  • Determinism. A memory access whose latency depends on TLB hit or miss is non-deterministic. Hard real-time code cannot tolerate this.
  • Power. Page-table walks burn cycles and memory bandwidth. For a battery-powered sensor that sleeps most of the time, an MMU is pure overhead.
  • Silicon. A useful MMU with a multi-entry TLB takes meaningful die area. M-profile aims for tiny.

What M-profile offers instead is the MPU — Memory Protection Unit — covered in detail in Topic 06. The MPU divides physical memory into a few regions (typically 8 or 16) and assigns access rules to each. No translation, just permissions. Deterministic, cheap, and sufficient for an RTOS to isolate tasks from each other without an MMU's overhead.

Test code — cache effect measurement

This experiment shows the cache earning its keep. We allocate a buffer, then read it twice — the first read warms the cache, the second hits it. The cycle counts should differ dramatically on a cached core, and be identical on a non-cached core.

Ccache_effect.c
#include <stdint.h>
#include <stdio.h>
#include "core_cm7.h"

#define N       4096
static uint32_t data[N] __attribute__((aligned(32)));

static uint32_t sum_buffer(const uint32_t *p, size_t n)
{
    uint32_t s = 0;
    for (size_t i = 0; i < n; i++) s += p[i];
    return s;
}

void cache_demo(void)
{
    /* Fill the buffer with arbitrary data */
    for (int i = 0; i < N; i++) data[i] = i;

    /* Drop all D-cache lines so we start cold */
    SCB_InvalidateDCache();

    uint32_t t0 = DWT_CYCCNT;
    sum_buffer(data, N);              /* COLD: misses cache */
    uint32_t t1 = DWT_CYCCNT;

    sum_buffer(data, N);              /* WARM: hits cache */
    uint32_t t2 = DWT_CYCCNT;

    printf("Cold pass (cache miss): %lu cycles\n", t1 - t0);
    printf("Warm pass (cache hit) : %lu cycles\n", t2 - t1);
    printf("Speedup               : %.2fx\n",
           (float)(t1 - t0) / (float)(t2 - t1));
}

Typical output on a Cortex-M7 with D-cache enabled, sumimg 16 KB of data:

ConsoleSWO output
Cold pass (cache miss): 12450 cycles
Warm pass (cache hit) :  4180 cycles
Speedup               : 2.98x

The same code on a Cortex-M4 (no cache) would show identical cycle counts for both passes — every access pays the same SRAM latency. That single number — same vs different — tells you instantly whether your cache is working.

Interview Questions

Interview Q & A — Cache & MMU

Q1. Why does code that works on a Cortex-M4 sometimes corrupt DMA buffers on a Cortex-M7?

Because the M7 has a D-cache and the M4 doesn't, and DMA bypasses the cache.

The typical failure: code reads a buffer (cache pulls in the line as zeros), then DMA writes new data into the same SRAM addresses (cache is now out of date), then code reads the buffer again and the cache happily returns the stale zeros it already has. The new data is in SRAM but the CPU never sees it.

Three fixes: (1) place the buffer in DTCM, which is outside the cache; (2) configure the MPU to mark the buffer region non-cacheable; (3) call SCB_InvalidateDCache_by_Addr() before reading. For DMA transmits, call SCB_CleanDCache_by_Addr() before starting the DMA so dirty cache lines reach SRAM first.

Q2. What is the difference between invalidate, clean, and clean & invalidate cache operations?

Invalidate marks cache lines as no-longer-valid. The next CPU read at those addresses misses the cache and fetches from memory. Used before a DMA receive — drops any stale lines so the next read sees the DMA's fresh data.

Clean writes dirty cache lines back to memory but leaves them valid in the cache. Used before a DMA transmit — ensures the buffer in memory is up to date so DMA reads correct data.

Clean and invalidate does both: writes back any dirty data, then drops the lines from the cache. Used at the end of a memory region's lifetime, or when memory is going to be reused for a different purpose.

Q3. What's the difference between write-back and write-through caching?

Write-back updates only the cache line on a write; the dirty line is written to memory only when it's evicted (or when explicit clean is requested). This is faster — most writes never touch main memory — but the cache and memory can be temporarily inconsistent. This is the default on Cortex-M7.

Write-through updates the cache and main memory on every write. Slower for writes, but memory is always coherent with the cache. Useful for memory regions that are also read by DMA or by another bus master — write-through plus invalidate-before-DMA-receive is a clean pattern.

The policy is configured per memory region via the MPU on Cortex-M7. Different regions of the address space can use different policies.

Q4. What is a TLB, and why does it matter on a Cortex-A system?

The Translation Lookaside Buffer is a small associative cache of virtual-to-physical address translations. Without it, every memory access would require the MMU to walk the page tables — multiple memory reads — before the actual access could happen.

With a TLB, common translations are cached, so the typical memory access is one extra cycle for the TLB lookup. TLB misses are expensive: typically 5–20 cycles for a page-table walk plus any cache misses along the way.

Why it matters: TLB performance dominates the cost of context switches in an OS. When the kernel switches processes, the TLB is invalidated, so the new process suffers a flurry of TLB misses for its first several hundred instructions. This is the main reason why kernels try to minimize context switches and why "userspace networking" frameworks bypass kernel boundaries entirely.

Q5. Why does the Cortex-M profile have no MMU?

Three deliberate reasons: determinism, power, and silicon area.

An MMU introduces non-deterministic memory access latency — every load and store depends on TLB state. Hard real-time code (interrupt handlers in motor controllers, audio inner loops, automotive ECUs) cannot tolerate variable timing. M-profile guarantees a memory access takes a known number of cycles, every time.

An MMU consumes power even when idle (the TLB has state to maintain) and burns cycles on every page-table walk. A battery sensor that sleeps 99% of the time cannot afford this overhead.

An MMU with a useful TLB takes significant die area. M-profile targets tiny silicon — 32 cents per chip in volume. The MPU provides the security and isolation that an RTOS actually needs, in a much smaller package.

Q6. When porting firmware from Cortex-M4 to Cortex-M7, what should you audit first?

In rough order of how often each is the source of bugs:

One: any code that touches DMA. Every DMA buffer needs cache awareness — either placed in DTCM, marked non-cacheable in the MPU, or wrapped with explicit clean/invalidate calls. This is the single most common porting failure.

Two: linker script and section placement. The M7 typically has DTCM and ITCM regions that the M4 didn't. Decide what goes in them — hot ISRs in ITCM, DMA buffers in DTCM is a good start. The linker script needs to define these regions.

Three: alignment. Cache lines on M7 are 32 bytes. Buffers that get DMA'd should be 32-byte aligned and their lengths should ideally be multiples of 32. Otherwise the cache maintenance operations may affect adjacent unrelated data.

Four: timing assumptions. Tight loops that ran at predictable speeds on M4 may now run faster (cache hits) or slower (cache misses) on M7. Anything that depended on cycle-accurate timing through software loops needs review — most should be using timers anyway.

Five: stack size. The M7 stacks more state on exception entry if FPU is in use. Bump task stack sizes by at least 100 bytes when porting, then reduce after measuring.
