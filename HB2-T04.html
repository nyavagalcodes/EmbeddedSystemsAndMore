Pipeline, Branch Prediction & Performance Counters

Three stages on a Cortex-M3, six on an M7, seven on an M85. Knowing what runs in parallel — and what stalls — is the difference between code that hits its timing budget and code that doesn't.

Every modern CPU is a pipeline. The Cortex-M cores differ dramatically in how deep their pipelines are, whether they can issue more than one instruction per cycle, and whether they predict branches. These choices shape which optimizations actually matter — and which "obvious" optimizations are wasted effort because the pipeline is already doing the work for you.

This topic shows you what is happening inside each Cortex-M pipeline, where stalls come from, and how to measure cycle-accurate performance using the DWT cycle counter — the closest thing to a profiler that an MCU has.

What a pipeline actually does

A simple non-pipelined CPU executes one instruction completely before starting the next: fetch, decode, execute, retire, then move on. A pipelined CPU overlaps these phases. While instruction N is in the execute stage, instruction N+1 is being decoded, and instruction N+2 is being fetched. In steady state, the CPU retires one instruction per cycle even though each instruction takes three or more cycles end-to-end.

Three-Stage Pipeline (Cortex-M3 / M4) cycle: 1 2 3 4 5 6 7 8 ───────────────────────────────────────────────── insn 1: F D E insn 2: F D E insn 3: F D E insn 4: F D E insn 5: F D E insn 6: F D E F = Fetch D = Decode E = Execute Steady state: one instruction retires every cycle. Cost of a flush (e.g. unpredicted branch): 2 cycles.

Key Idea

Deeper pipelines extract more performance from straight-line code but pay a bigger penalty for every mispredicted branch. A Cortex-M7 may waste five or six cycles on a misprediction; a Cortex-M0+ wastes one. This is why M0+ is competitive on branch-heavy state machines despite its much lower clock — there's nothing to flush.

Where stalls come from

A pipeline is only as fast as its slowest stage, and several common patterns cause it to stall:

1. Memory access latency

If an instruction needs data from external memory (or even flash with wait states), the execute stage stalls waiting for the load to complete. The pipeline cannot retire the load instruction, so everything behind it queues up.

Cortex-M7 mitigates this with caches and TCMs. Cortex-M3 and M4 mitigate it with flash accelerators — small instruction caches that prefetch sequential code so the pipeline rarely stalls on flash access.

2. Branch mispredictions

When the CPU encounters a conditional branch, it must guess which way the branch will go and start fetching from that target. If the guess is wrong, the speculatively fetched instructions are discarded and the pipeline refills from the correct target. The cost is approximately the pipeline depth in cycles.

Cortex-M3/M4 use a simple static predictor: backward branches are predicted taken (loops), forward branches not taken (skip-the-error case). Cortex-M7 and M85 use a dynamic predictor that learns from runtime behaviour.

3. Data hazards

If instruction N writes R0, and instruction N+1 reads R0, the CPU must wait until the write completes before the read can start. Modern cores use forwarding to bypass the register file and deliver the result directly to the next instruction, eliminating most of these stalls. But complex dependencies (an integer-multiply followed by a divide, for example) can still cost cycles.

4. Pipeline flushes on exceptions

When any exception fires, the entire pipeline is flushed. On a Cortex-M7, that costs roughly six cycles before the first instruction of the handler can execute — on top of the architectural exception entry overhead. This is one reason high-frequency interrupts can become a significant load even on a fast core.

The DWT cycle counter

The Data Watchpoint and Trace unit sits in the PPB at 0xE0001000. It includes a free-running 32-bit cycle counter that ticks every CPU clock cycle. This is the single most useful piece of hardware for measuring real performance on a Cortex-M.

Cdwt_cycles.c
#include <stdint.h>
#include <stdio.h>

#define DWT_CTRL       (*(volatile uint32_t *)0xE0001000UL)
#define DWT_CYCCNT     (*(volatile uint32_t *)0xE0001004UL)
#define DEMCR          (*(volatile uint32_t *)0xE000EDFCUL)
#define DEMCR_TRCENA   (1UL << 24)
#define DWT_CTRL_CYCCNTENA  (1UL << 0)

void dwt_init(void)
{
    DEMCR     |= DEMCR_TRCENA;          /* enable tracing block */
    DWT_CYCCNT  = 0;                       /* reset counter */
    DWT_CTRL  |= DWT_CTRL_CYCCNTENA;    /* start counter */
}

static inline uint32_t dwt_get_cycles(void)
{
    return DWT_CYCCNT;
}

/* Measure cycles around an arbitrary block of code. */
#define MEASURE_CYCLES(name, code) \
    do { \
        uint32_t _start = dwt_get_cycles(); \
        code; \
        uint32_t _end = dwt_get_cycles(); \
        printf("%-30s : %lu cycles\n", name, _end - _start); \
    } while (0)

Once dwt_init() has been called, the counter free-runs and rolls over every 2³² cycles — that's about 25 seconds at 168 MHz, plenty for any micro-benchmark. To measure code, snapshot the counter before and after.

A worked example — measuring branch cost

This is the kind of measurement that turns intuition into knowledge. Three versions of the same trivial function, each with different branch behaviour, measured on a Cortex-M4 at 168 MHz with the flash accelerator on.

Cbranch_bench.c
/* Version A: predictable branch (always taken).
 * Static predictor: backward branch = taken. Should hit.   */
static uint32_t sum_predictable(const uint32_t *p, size_t n)
{
    uint32_t sum = 0;
    for (size_t i = 0; i < n; i++) sum += p[i];
    return sum;
}

/* Version B: data-dependent branch on random data.
 * Predictor cannot guess; each iteration may misprediction. */
static uint32_t sum_branchy(const uint32_t *p, size_t n)
{
    uint32_t sum = 0;
    for (size_t i = 0; i < n; i++) {
        if (p[i] & 1) sum += p[i];
    }
    return sum;
}

/* Version C: branchless version of B using conditional add.
 * Compiler emits IT block or conditional add — no branch. */
static uint32_t sum_branchless(const uint32_t *p, size_t n)
{
    uint32_t sum = 0;
    for (size_t i = 0; i < n; i++) {
        sum += (p[i] & 1) * p[i];   /* 0 or p[i] */
    }
    return sum;
}

void run_benchmark(void)
{
    static uint32_t data[1024];
    for (int i = 0; i < 1024; i++)
        data[i] = rand();              /* unpredictable LSBs */

    MEASURE_CYCLES("predictable",    sum_predictable(data, 1024));
    MEASURE_CYCLES("data-branchy",   sum_branchy(data, 1024));
    MEASURE_CYCLES("branchless",     sum_branchless(data, 1024));
}

Typical results on a Cortex-M4 at 168 MHz, compiled with -O2:

ConsoleSWO output
predictable                    : 5160 cycles    (~5 cyc/element)
data-branchy                   : 8290 cycles    (~8 cyc/element)
branchless                     : 6210 cycles    (~6 cyc/element)

Three lessons in one experiment:

  1. Predictable loops run near 5 cycles per element — close to the theoretical minimum (load, add, increment, branch).
  2. Data-dependent branches add roughly 3 cycles per element of misprediction penalty on random data.
  3. Branchless code (using conditional add or multiply) beats the data-branchy version by skipping the predictor entirely.
When branchless is worse

Branchless tricks pay off when the branch is genuinely unpredictable. If your branch is predictable 95% of the time, the predictor will get it right almost always, and the branchful version will be faster than the branchless one. Always measure before believing the textbook.

Other useful DWT counters

The cycle counter is just the headline feature. DWT also includes:

RegisterWhat it counts
CYCCNTFree-running cycle counter (the main one)
CPICNTCycles per instruction overhead — extra cycles where the CPU could not retire one instruction per cycle
EXCCNTCycles spent in exception entry and exit
SLEEPCNTCycles the CPU spent in sleep mode
LSUCNTCycles spent in load-store operations beyond one cycle
FOLDCNTCycles saved by instruction folding (a Cortex-M3/M4 optimization)

Reading CPICNT alongside CYCCNT is how you measure the actual CPI (cycles per instruction) of a region of code. If CPICNT is large compared to CYCCNT, the code is stalling on memory or branch mispredictions.

The Cortex-M7 dual-issue twist

Cortex-M7 can dual-issue certain instruction pairs — execute two instructions in the same cycle if they do not depend on each other and they use different functional units. The ARM Cortex-M7 Technical Reference Manual lists which pairs qualify; the general rule is that you can pair a simple ALU operation with a load, or with a branch, or with a multiply.

This is why a Cortex-M7 at 480 MHz can deliver more than just a clock-ratio improvement over a Cortex-M4 at 168 MHz. Roughly: the M4 does ~1 IPC, the M7 does ~1.4 IPC on typical code, so the real speed-up is closer to 4× than the 2.9× the clocks alone would suggest.

Key Idea

For a function-level performance number, the formula is approximately:
time = (cycles / IPC) / clock_speed. On M0/M0+, IPC ≈ 0.6 (lots of stalls). On M3/M4, IPC ≈ 0.9. On M7, IPC can reach 1.4. On M85, with both dual-issue and Helium, vector code can effectively do 4 or 8 "elements" per cycle on SIMD data — IPC stops being a useful metric once vectors enter the picture.

Interview Questions

Interview Q & A — Pipeline & Counters

Q1. What is the cost of a branch misprediction on a Cortex-M4 versus a Cortex-M7?

Approximately the depth of the pipeline. Cortex-M4 has a 3-stage pipeline, so a mispredicted branch costs roughly 2 cycles — the two instructions speculatively fetched but not used must be discarded.

Cortex-M7 has a 6-stage pipeline, so the cost rises to about 5 cycles. This is why the M7 invests in a much more accurate branch predictor: the cost of getting it wrong is higher.

You can measure this directly by running the same data-dependent branch loop on both cores and comparing cycle counts via DWT.

Q2. How do you measure execution time of a function with cycle accuracy on a Cortex-M?

Use the DWT cycle counter. The setup is three writes:

  1. Set CoreDebug->DEMCR.TRCENA = 1 to enable the trace block.
  2. Clear DWT->CYCCNT = 0.
  3. Set DWT->CTRL.CYCCNTENA = 1 to start the counter.

After that the counter free-runs at the CPU clock. Snapshot it before and after the code you want to measure, subtract, and that's your cycle count.

Caveat: the counter is 32 bits, so it rolls over every 2³² cycles — about 25 seconds at 168 MHz. For longer measurements, sample more often and accumulate.

Q3. When is branchless code faster than branchful, and when is it slower?

Branchless is faster when the branch is unpredictable. On data with no exploitable pattern, the branch predictor fails roughly half the time, and each misprediction costs the pipeline depth in cycles. Replacing the branch with a conditional move, multiply, or arithmetic mask avoids the penalty entirely.

Branchless is slower when the branch is predictable. If the branch goes the same way 95% of the time, the predictor wins almost always, and the branchful version does no extra work. The branchless version still computes both sides of the conditional, so it does more work per iteration.

Rule of thumb: measure. Use DWT to compare, and the answer will be obvious.

Q4. What is dual-issue, and which Cortex-M cores support it?

Dual-issue means the CPU can decode and dispatch two instructions in the same cycle, provided they do not depend on each other and use different functional units. For example, an ALU operation and a memory load can issue together; two ALU operations on the same register cannot.

Among Cortex-M cores, only the M7 and M85 support dual-issue. The M3, M4, M33, and M55 are all single-issue. This is part of why the M7 can deliver well over 2× the per-MHz throughput of a Cortex-M4, not just the clock-frequency ratio.

On vector-capable cores (M55, M85), there is a separate vector pipeline that can run in parallel with scalar instructions — effectively a different kind of dual-issue.

Q5. Why does an exception cost more cycles than just the architectural overhead listed in the manual?

Three reasons stack up:

Pipeline flush. The CPU must discard everything it had speculatively fetched. On a deep pipeline like M7's, that costs roughly the pipeline depth.

Stacking. The hardware pushes 8 registers (or 26 with FPU active) to the stack. Each push is a memory write, and writes to slow memory (off-chip SRAM, for instance) stall until completed.

Vector fetch. The CPU reads the handler address from the vector table — a memory access that may itself miss the cache or hit flash with wait states.

Add it all up and the "12 cycles" the manual quotes for exception entry on a Cortex-M3 can be 20+ cycles in practice on a real chip with cached flash. Measure with DWT to see your actual numbers.

Q6. Why is the M0+ pipeline shorter than the M0 pipeline, and what's the practical benefit?

The M0+ is a redesign that targets even smaller silicon and lower power than the M0. ARM took the 3-stage M0 pipeline and merged two stages into one, producing a 2-stage pipeline (combined fetch+decode, then execute).

The practical benefit: branch penalty drops from 2 cycles to 1 cycle. On branch-heavy code (state machines, event handlers, bit-banged protocols), this gives M0+ better per-MHz throughput than M0. Combined with M0+'s optional single-cycle GPIO port, it is materially better for the tiny-MCU use cases.

The trade-off is that decode logic must complete in roughly the same time as a single fetch, which limits maximum clock frequency. M0+ tops out around 50 MHz in typical silicon; M0 can clock slightly higher because each stage is simpler.
